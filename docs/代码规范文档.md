# O-Doc 代码与架构规范

本文档是 O-Doc 前后端开发、重构与评审的统一规范。本项目以个人开发为主，规范的目标是用尽量低的维护成本保证代码清晰、行为可靠和数据安全，不追求企业级流程或为了形式增加抽象层。

文中的“必须/禁止”用于安全、数据一致性、接口契约和容易引发故障的问题；“应/优先”表示默认做法，在有明确理由时可以采用更简单的实现；“建议”不作为功能交付的硬性门槛。历史代码在修改相关区域时逐步迁移，不要求无关代码一次性改造。

## 1. 通用原则

- 先理解现有模块、数据同步和接口契约，再开始修改。修改前检查工作区状态，不覆盖、回退或顺带格式化已有的无关改动。
- 一次改动聚焦一个可验证目标。功能变更应包含相应测试或可复现的人工验收步骤。纯重构默认只调整代码结构，不得顺带改变原有业务逻辑、数据处理、接口契约、交互流程、设计语言和 UI 视觉表现。
- 若重构过程中确实需要修复既有逻辑或优化 UI，必须将其作为明确的行为变更说明；能拆分时与结构重构分开提交或分阶段实施，不能以“顺手优化”为由混在纯重构中。
- 以职责和变化原因拆分代码，不机械按行数拆文件。一个模块同时承担页面编排、请求细节、复杂业务计算和大量 UI 渲染，且已经难以理解或测试时，应按职责拆分。
- 前端组件约 300 行、单个函数约 80 行只作为复查信号，不是硬性上限。若代码围绕单一高内聚职责，拆分后反而产生大量状态传递或中转层，可以保留在同一文件中。
- 不创建只转发 props、样式或函数且没有独立职责的 Wrapper/Shell，也不为了满足目录形式创建空洞的 service、Hook 或工具文件。抽取出的模块应有明确的输入、输出和职责。
- 新增或修改模型、字段、同步数据、导入导出格式和 API 时，必须同时检查 `docs/数据同步逻辑说明.md`、相关 WebDev 同步逻辑、迁移、前端类型和兼容性。
- 注释解释业务原因、约束或非显而易见的取舍，不复述代码。删除失效注释、无效注释代码和临时调试输出。

## 2. 命名、类型与接口契约

- 前端变量、函数和 API 字段使用 `camelCase`；React 组件和类型使用 PascalCase；Hook 以 `use` 开头；常量根据语义使用 `camelCase` 或 `UPPER_SNAKE_CASE`。
- 后端 Python 变量、函数、模型字段和序列化器字段使用 `snake_case`；类使用 PascalCase；常量使用 `UPPER_SNAKE_CASE`。URL 路径保持项目现有风格，同一组接口内不得混用多种命名方式。
- 已配置 `djangorestframework-camel-case`：前端发送的驼峰字段由后端自动解析为下划线，后端响应字段自动渲染为驼峰。前端不得重复手写通用字段转换，后端不得为迎合前端把模型字段改成驼峰。
- 成功和错误响应继续使用 `utils.response_utils` 及既有 `code`、`msg`、`data` 契约。新接口和修改到的错误路径应同时使用合理的 HTTP 状态码；不得只依赖文案判断错误类型，也不得在单个接口中另起不兼容的响应结构。
- 新增业务模型、API 入参/响应、组件 props 和 Hook 边界应有明确类型，不得以 `any` 代替本可清楚表达的核心契约。第三方库缺少类型、动态内容适配或渐进迁移时允许局部使用 `any`；能安全接收未知数据时优先使用 `unknown` 和类型守卫，并避免让 `any` 扩散到模块边界。
- `@ts-ignore`、`eslint-disable` 等规则抑制必须限定到最小范围并说明原因；能够表达预期类型错误时优先使用 `@ts-expect-error`。
- Python 对 service、跨模块边界和复杂入参/返回值应添加类型标注；简单 Django 视图和局部变量不要求为了形式补全类型。
- API 字段、事件名、数据同步格式和持久化字段属于兼容契约。用户可见文案仅在业务确实依赖其内容时视为契约；纯重构不得无意改变兼容行为。

## 3. 前端架构（React + TypeScript）

前端以现有 `frontend_react/src` 为基础，保持依赖大致由页面和领域模块流向基础能力：

```text
App / layout → views → feature components / hooks → api / utils / types / constants
                         ↘ common components / contexts
```

- `App.tsx`、`layout/` 负责应用壳、路由、布局、全局 Provider 和跨页面初始化，不承载具体业务页面的大量实现。
- `views/` 是页面组合层，负责路由参数、页面级状态、权限入口和领域模块编排。页面可以决定何时加载或刷新数据，但后端业务请求应通过领域 Hook 或 `api/` 中的有类型函数完成，不在 JSX 中直接处理 Axios 和响应协议。
- `components/<Domain>/` 存放领域展示与交互组件；`components/common/` 只放真正跨领域、相对稳定的基础 UI。只服务单页的组件不必提前放入 `common`。
- `hooks/` 负责确有复用价值或能明显降低页面复杂度的状态、生命周期和异步流程。简单弹窗开关、输入值和局部筛选可留在页面或组件中，不强制为每段逻辑创建 Hook。
- 只有确实跨页面共享的状态才进入 `contexts/` 或其他全局状态容器。优先保持状态靠近使用位置，避免建立难以追踪的全局可变状态。
- `api/` 是后端业务 HTTP 调用的统一入口，负责 URL、请求参数和返回类型。静态资源、地图文件、Worker、流式协议或文件下载允许使用专用 `fetch`/transport，但应集中封装，不在多个组件中重复认证和错误解析逻辑。
- `types/` 存放跨组件或跨 API 的契约，`constants/` 存放稳定常量，`utils/` 存放无 React 状态、可独立测试的函数。领域私有类型和工具可与领域模块就近放置，不要求全部提升到全局目录。

### 前端实现要求

- 组件应有单一、可描述的主要职责。复杂 JSX、事件处理或派生计算只有在影响理解、测试或复用时才提取，不为缩短文件而拆分。
- 所有用户可感知的异步请求应处理 loading、失败和空数据。可能并发或乱序的搜索、筛选、切换详情等请求，使用 `AbortController`、请求序号或等价机制，避免旧响应覆盖新状态。
- Effect 用于与浏览器 API、网络、订阅或第三方实例等外部系统同步。能在 render 中计算的派生数据、普通事件逻辑和 props 到 state 的机械复制不应放入 Effect。
- `useEffect` 创建的事件监听、定时器、订阅、对象 URL 和取消控制器必须在 cleanup 中释放；依赖项应完整。确需绕过依赖规则时必须说明原因并验证不存在闭包过期问题。
- 不在 render 期间执行请求、写存储、生成影响输出的不稳定随机值或其他副作用。`useMemo`、`useCallback` 仅在改善正确性或可测量性能时使用。
- 使用 `rehypeRaw`、`dangerouslySetInnerHTML` 或注入 SVG/HTML 时，只能渲染可信内容，或在渲染前进行可靠过滤；不得直接渲染未经处理的用户输入、网页内容或 AI 输出。
- 交互控件应优先使用语义化 HTML，并保证常用键盘操作、焦点可见和必要的 `aria-label`。复杂无障碍体系、路由懒加载和额外 Error Boundary 可按实际用户和性能需要逐步增加，不作为普通改动的硬性要求。
- 样式遵从 `docs/UI设计规范文档.md`。优先复用现有设计 token、Tailwind 工具类和公共组件；新增样式应限定在组件或领域范围，避免无前缀的全局选择器和重复 token。
- 拆分或重构页面/组件时，应保持原有 DOM 语义、布局尺寸、间距、颜色、字体、层级、响应式表现、动画、交互反馈和键盘行为。除非任务明确要求设计调整，不得因更换组件结构、公共组件或样式写法而产生可见变化。
- UI 等价性必须使用真实数据，同时检查空数据、加载、错误、弹窗、窄屏/宽屏和主要交互状态；不得只以空数据页面或单张静态截图作为验收依据。需要体验优化时，在结构重构稳定后作为独立行为变更处理。

## 4. 后端架构（Django + DRF）

- 以 Django app 作为主要领域边界。`models.py` 描述数据模型及紧邻模型的不变量；`serializers.py` 负责请求/响应序列化和字段校验；`views.py` 负责 HTTP 参数、权限、调用业务能力和返回响应；`urls.py` 只声明路由。
- 简单 CRUD 可以直接由 View、Serializer 和 Model 完成。只有跨多个模型、外部服务、文件处理、同步或明显复杂的业务流程，才提取到 app 内命名明确的 service/module；不强制引入 repository、selector、use case 等额外分层。
- `utils/` 只放真正通用、没有清晰领域归属的能力。领域逻辑优先留在对应 app，避免把 `utils/` 变成新的万能目录。
- 数据库访问使用 ORM，容易产生 N+1 的列表和嵌套序列化应使用 `select_related`、`prefetch_related` 或聚合优化。多表一致性写操作使用 `transaction.atomic()`；耗时外部 I/O 尽量不要放在长事务中，提交后副作用可使用 `transaction.on_commit()`。
- 迁移必须由 Django migration 管理，不手改生产表结构。高风险的数据迁移、字段删除或同步字段变化必须先确认备份、兼容性和 WebDev 同步影响；普通个人部署不要求采用完整的零停机迁移流程。
- 外部 I/O（AI、RAG、存储、飞书、同步）必须设置合理超时、处理异常并提供可定位上下文；不得裸 `except`、无声吞掉关键异常或向客户端泄露密钥、堆栈和内部配置。清理资源时允许捕获宽泛异常，但应说明其不会掩盖主流程故障。
- 私有资源读取和写操作必须在服务端校验认证、权限及必要的对象归属。公开接口可显式使用 `AllowAny`，但应能从代码或注释看出其公开原因；不引入不必要的复杂 RBAC。
- 登录、同步、上传、删除、AI/MCP 调用等敏感或高成本接口应根据实际部署范围考虑限流、大小限制和重复提交保护。
- 后台调度、线程和 WebSocket 生命周期须具备幂等启动、停止/清理和异常保护。会产生重复数据或重复通知的任务必须有最小必要的互斥或幂等机制，不要求为普通任务建立完整分布式任务平台。

## 5. 安全与日志底线

- 密码、Token、模型/API 密钥、远程存储凭据和完整认证请求头不得写入仓库、返回给客户端或输出到日志。配置通过环境变量或现有安全配置机制提供。
- 网页抓取、远程下载和可配置回调地址必须校验协议和目标，避免访问不应暴露的本机、内网或云元数据地址；重定向后的目标也应纳入校验。
- 文件上传必须校验大小、允许的类型和最终保存路径；不能只信任扩展名或客户端声明的 MIME 类型。用户上传内容不得作为可执行文件提供。
- 业务代码使用 Python `logging` 或前端统一错误处理记录问题，不新增随意的 `print`、`console.log`。日志应包含能定位问题的资源 ID、任务 ID 或操作阶段，但必须脱敏。
- 可恢复的预期异常给出清晰提示；未知异常记录必要上下文后返回统一错误，不将堆栈和内部路径暴露给前端。个人项目不强制接入集中式日志、链路追踪或监控平台。

## 6. 依赖、环境与配置

- 前端使用 Node.js 22，并保持 `.nvmrc`、`package.json` 和 Docker 环境一致。提交 `package-lock.json`；本地可使用 `npm install`，CI 或 Docker 构建优先使用 `npm ci` 保证可复现。
- 后端使用 uv 管理的 Python 3.11 环境。当前可继续以 `requirements.txt` 作为依赖清单，不强制立即迁移到 `pyproject.toml + uv.lock`；升级依赖时应单独验证并避免在普通功能改动中顺带大范围升级。
- 开发和生产配置通过环境变量区分。生产环境不得启用 Django DEBUG，不得使用开发密钥；公网或非可信网络部署时应配置明确的 `ALLOWED_HOSTS`、HTTPS 和必要安全头。
- 生产部署或部署配置变化时运行 Django `check --deploy`；普通本地功能开发不要求每次运行部署检查。
- 不提交构建产物、真实数据、数据库备份、临时调试文件和包含隐私的日志；确需提交的示例配置只保留安全占位值。

## 7. 测试、校验与验收

采用风险驱动的验证方式，不要求每次改动运行所有测试，也不设置形式化覆盖率门槛：

- 普通文案和样式调整：至少进行相关页面人工验证；能快速运行时同时执行 type-check。
- 前端逻辑、Hook、组件行为或构建配置：按影响运行 `npm run lint`、`npm run type-check`、相关测试或 `npm run build`。涉及白板或图片上传逻辑时，分别运行 `npm run test:whiteboard`、`npm run test:image-upload`。
- 后端使用项目 uv + Python 3.11 环境运行 Django 检查和受影响测试。新增纯业务规则应优先写成可独立测试的函数或 service。
- Bug 修复在问题能够稳定复现且测试成本合理时，应补充回归测试；一次性视觉问题或依赖真实 AI 输出的效果允许以人工验收为主。
- 同步、导入导出、删除、权限、迁移和数据一致性属于高风险改动，必须验证正常、失败、重复执行和关键边界路径，并确认 WebDev 同步影响。
- 外部 AI、RAG、飞书、MCP 和远程存储的自动化测试应使用 mock/fake，普通测试不得依赖真实密钥、网络服务或开发机已有数据。
- API 修改至少验证请求校验、权限、HTTP/业务错误、字段命名转换和前端类型。页面修改检查真实数据、空数据、加载、错误、常用尺寸、弹窗和关键键盘操作。
- 提交前检查变更范围、遗留调试输出、密钥和无关文件。若无法运行某项重要校验，说明未运行项、原因和已采取的替代验证即可。

## 8. 重构工作流

1. 阅读 `docs/项目结构文档.md`，确认待改模块的边界、调用方和数据同步影响。
2. 列出需要保持的接口、业务逻辑、交互、状态和视觉契约；涉及 UI 时记录关键页面及真实数据下的重构前基线，选择与风险相称的验证方式。
3. 优先处理最明确的职责边界；不要求固定按照“纯逻辑、类型、数据访问、UI”的顺序拆分，只要每一步保持可运行且便于检查。
4. 新模块放入最接近其职责的目录，避免循环依赖、跨领域深层导入和无意义中转层。
5. 运行受影响校验并完成必要的人工验收，对照重构前基线确认没有非预期的逻辑或视觉变化；清楚区分行为变更与结构调整。
