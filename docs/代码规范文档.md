# O-Doc 代码与架构规范

本文档是 O-Doc 前后端开发、重构与评审的统一规范。所有新功能、缺陷修复和重构均须遵循本文档；历史代码可在修改相关区域时逐步迁移，不要求无关代码一次性改造。

## 1. 通用原则

- 先理解现有模块、数据同步和接口契约，再开始修改。修改前检查工作区状态，不覆盖、回退或顺带格式化用户已有的无关改动。
- 一个提交聚焦一个可验证目标。功能变更须包含相应测试或可复现的人工验收步骤；纯重构须证明接口、行为和视觉表现等价。
- 以职责边界拆分代码，而不是机械按行数拆文件。禁止新增“万能”页面、组件、Hook、视图、服务或工具文件；一个文件不得同时承担页面编排、状态管理、请求、复杂业务计算和 UI 渲染等多种职责。
- 当模块出现两个及以上独立变化原因，或函数/组件已难以整体理解和测试时，应按领域、交互区块、数据访问或纯业务逻辑拆分。可将前端组件约 300 行、单个函数约 80 行作为复查信号，而非规避职责拆分的硬性上限。
- 不创建只转发 props、样式或函数且没有独立职责的 Wrapper/Shell。抽取出的模块必须有明确名称、输入、输出与资源所有权。
- 新增或修改模型、字段、同步数据、导入导出格式和 API 时，必须同时检查 `docs/数据同步逻辑说明.md`（及相关 WebDev 同步逻辑）、迁移、前端类型和兼容性。
- 注释解释业务原因、约束或非显而易见的取舍，不复述代码。删除失效注释和无效的注释代码。

## 2. 命名、类型与接口契约

- 前端 TypeScript 代码、类型、变量、函数和 API 字段使用 `camelCase`；React 组件使用 PascalCase，Hook 以 `use` 开头。
- 后端 Python 代码、Django 模型字段、序列化器字段和 URL 内部命名使用 `snake_case`；类使用 PascalCase；常量使用 `UPPER_SNAKE_CASE`。
- 已配置 `djangorestframework-camel-case`：前端发送的驼峰字段由后端自动解析为下划线，后端响应字段自动渲染为驼峰。前端不得重复手写字段转换，后端也不得为迎合前端把模型字段改成驼峰。
- 成功和错误响应使用 `utils.response_utils` 及既有统一响应契约（`code`、`msg`、`data`）。不得在单个接口中另起不兼容的响应结构。
- TypeScript 中禁止用 `any` 绕过类型；为接口入参、响应、组件 props、Hook 返回值和复杂状态定义可复用类型。Python 对跨模块边界、复杂入参/返回值优先添加类型标注。
- API 字段、事件名、数据同步格式、持久化字段和用户可见文案都是兼容契约；纯重构不得擅自改变它们。

## 3. 前端架构（React + TypeScript）

前端以现有 `frontend_react/src` 目录为基础，依赖方向如下：

```text
App / layout → views → components / hooks → api / utils / constants / types
                                      ↘ contexts
```

- `App.tsx`、`layout/` 仅负责应用壳、路由/布局、全局 Provider 和跨页面初始化，不承载具体业务页面实现。
- `views/` 是页面组合层：处理路由参数、页面级权限与多个领域模块的编排；不要在页面中堆积可复用卡片、弹窗、复杂表格逻辑或请求细节。
- `components/<Domain>/` 存放对应领域的展示与交互组件，`components/common/` 只放真正跨领域、稳定的基础 UI。禁止把只服务单页的组件放入 `common`，也禁止跨领域深层导入另一个领域的内部实现。
- `hooks/` 负责可复用状态、生命周期、异步流程和领域操作。局部弹窗开关、输入值、筛选条件等状态留在页面或领域组件；只有确实跨页面共享的状态才进入 `contexts/` 或其他全局状态容器。
- `api/` 是 HTTP 调用的唯一入口。组件和页面不得直接使用 axios、拼接 URL 或解析传输层细节；每个 API 文件按领域导出有类型的请求函数。
- `types/` 存放跨组件、跨 API 的数据契约，`constants/` 存放稳定业务常量，`utils/` 存放无 React 状态、可单独测试的纯函数。避免将领域规则散落在 JSX、事件回调或重复的工具函数中。
- 按需拆分大页面时，优先提取：页面容器、领域子组件、数据/交互 Hook、纯逻辑与类型；保持数据流单向清晰。子组件通过明确 props 和回调协作，不通过隐式修改父级状态。

### 前端实现要求

- 组件必须有单一、可描述的职责。复杂 JSX 区块应提取为语义明确的子组件；复杂事件处理和派生计算应提取为命名函数、Hook 或纯工具函数。
- 所有异步请求须处理 loading、失败和空数据。可能并发或乱序的搜索、筛选、切换详情等请求，使用 `AbortController`、请求序号或等价机制，避免旧响应覆盖新状态。
- `useEffect` 创建的事件监听、定时器、订阅、对象 URL 和取消控制器必须在 cleanup 中释放；依赖项须完整且稳定，禁止以关闭 lint 规则掩盖生命周期问题。
- 不在 render 期间执行请求、写存储、生成不稳定随机值或其他副作用。回调、memoization 仅在能改善正确性或性能时使用，不为形式而滥用。
- 样式遵从 `docs/UI设计规范文档.md`。优先复用现有设计 token、Tailwind 工具类和公共组件；新增样式必须限定在组件/领域范围，避免无前缀的全局选择器、重复 token 和依赖加载顺序的覆盖。
- 重构 UI 时先保证 DOM、交互、键盘行为、加载/错误状态和视觉等价，再单独进行体验优化；不得只以空数据页面作为验收依据。

## 4. 后端架构（Django + DRF）

- 以 Django app 为领域边界。`models.py` 只描述数据模型及紧邻模型的不变量；`serializers.py` 负责请求/响应序列化和字段校验；`views.py` 负责 HTTP 参数适配、权限、调用业务能力和返回统一响应；`urls.py` 只声明路由。
- 跨多个模型、外部服务、文件处理、同步或复杂业务流程，提取到 app 内命名明确的 service/module；通用且无领域归属的能力放入 `utils/`。视图、序列化器和信号中不得堆积大型业务流程。
- 数据库访问应通过 ORM，查询使用 `select_related`、`prefetch_related`、聚合等方式避免 N+1。涉及多表一致性的写操作使用 `transaction.atomic()`；迁移必须由 Django migration 管理，不手改生产表结构。
- 外部 I/O（AI、RAG、存储、飞书、同步）必须设置超时、处理异常并记录可定位上下文；不得吞掉异常、裸 `except` 或向客户端泄露密钥、堆栈和内部配置。
- 认证、授权和对象归属校验属于服务端职责。所有写操作和私有资源读取都必须显式校验权限，不能只依赖前端隐藏入口。
- 后台调度、线程和 WebSocket 生命周期须有幂等启动、停止/清理及异常保护，避免重复调度、重复消费或进程退出后残留资源。

## 5. 测试、校验与验收

- 前端日常至少运行与改动相符的校验：`cd frontend_react && npm run lint`、`npm run type-check`、`npm run build`。涉及白板或图片上传逻辑时，分别运行 `npm run test:whiteboard`、`npm run test:image-upload`。
- 后端使用项目 `uv` + Python 3.11 环境运行 Django 检查和受影响测试；新增可测试业务规则应优先写为纯函数或 service 测试，并覆盖正常、空值、权限、失败和边界路径。
- 修改 API 时至少验证请求校验、权限、错误响应、字段命名转换和前端类型。修改同步、定时任务或外部集成时，额外验证幂等性、失败重试/提示和数据一致性。
- 修改页面或样式时，人工检查真实数据、空数据、加载、错误、窄屏/宽屏、弹窗及关键键盘操作；确认页面切换后状态与资源释放符合预期。
- 提交前检查变更范围、依赖方向、遗留调试输出、密钥和无关文件。若无法运行某项校验，必须说明未运行项、原因和已采取的替代验证。

## 6. 重构工作流

1. 阅读 `docs/项目结构文档.md`，确认待改模块的边界、调用方和数据同步影响。
2. 列出需要保持的接口、行为、状态和视觉契约；先补充或确认可用的验证方式。
3. 先抽取纯逻辑、类型和数据访问，再拆分 UI 或视图编排；每一步保持可运行、可回退。
4. 新模块放入其职责目录，保持依赖由页面到领域、由领域到基础能力的单向流动。
5. 运行受影响校验并完成必要的人工验收；在提交说明中清楚区分行为变更与结构调整。
