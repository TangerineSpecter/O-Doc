# 需求：回收站二期（文集 + 图片 + 白板）

- 状态：可领取规格；建议排在 `003` 之后，可与 `004` 并行（**尽量不新模型**）
- 规划来源：`docs/功能规划文档.md` P0 回收站后续阶段；[001](./001-回收站一期.md) 第 9 节
- 对照现状：HEAD `b2852e9`，前端 `0.9.14`。`/recycle` 已有 Markdown 文章和闪念。文集、图片、白板删除已经是 `is_valid=False`，但界面仍写「无法恢复」，图片删除还会**立刻删掉资源文件**
- 无新同步协议；不升应用版本（不新增字段的前提下）

## 1. 要解决的问题

一期只接住了文章和闪念。现在：

- 首页删除文集：文案写「无法恢复，且文章一并移除」；后端其实只软删文集，子文章还在库里，只是因为文集无效而看不见
- 图片删除：软删 `Image`，但随即 `delete_asset_record_and_file`，恢复也救不回文件
- 白板删除：软删，文案写「无法恢复」，回收站没有入口

用户看到的是永久删除，库里却是半截软删，对不上。

## 2. 目标

登录用户能在现有 `/recycle` 里看到自己的已删**文集、图片、白板**，可以恢复或彻底删除。删除确认文案改成「将移入回收站」。图片的文件留到彻底删除再清。

## 3. 范围

### 做

- 文集：任意 `type`（文章 / 图片 / Agent / 图书），`is_valid=False`
- 图片：`article.Image` 且 `is_valid=False`（含拍摄组里被移出/删除的照片）
- 白板：`whiteboard.Whiteboard` 且 `is_valid=False`
- `/recycle` 筛选增加：文集 / 图片 / 白板（保留一期的文章、闪念、全部）
- 恢复、彻底删除（二次确认 + 同步墓碑，规则与 `001` 相同）
- 各入口删除文案从「无法恢复」改为「将移入回收站」
- **图片软删时不得再删 Asset 文件**；文件清理挪到彻底删除，且仍要检查没有其它图片/文章引用

### 不做

- 原样 HTML 笔记：维持不可恢复，不要混进文章或文集粉碎的默许级联里当「可恢复 HTML」
- 资源库（`Asset` 硬删除、共享引用），见现接口
- 图书单本、提示词模板（提示词已有自己的软删列表）
- 自动 30 天清空、新 `deleted_at` 字段（仍用软删后的 `updated_at` 当删除时间）
- 版本历史、分享链接、导出、双链

## 4. 产品规则

### 4.1 文集

1. 删除文集 = 只软删文集，**不**自动把子文章/图片/书放进回收站。它们继续挂着原来的 `coll_id`，只是列表里暂时看不见。
2. 回收站文集行要显示类型徽标，以及「其下仍有 N 篇/张/本」（按还存在的子记录计数，含已在回收站的文章）。
3. 恢复文集：`is_valid=True`。仍然有效的子内容回到原入口。已经单独进回收站的文章/图片保持在回收站。
4. 彻底删除文集：若仍有子文章、图片或图书记录，**默认拒绝**，说明数量，让用户先恢复文集再处理子项，或提供第二次确认「同时粉碎其下内容」。二次确认才级联粉碎子 Markdown 文章 / 图片 / 图书记录（HTML 笔记仍走现有不可恢复清理，不要新造可恢复 HTML）。
5. 一期规则仍然成立：所属文集无效时，文章恢复失败并提示先恢复文集。图片同样。

### 4.2 图片

1. 软删只改 `Image.is_valid` 和文集计数，更新本机视觉索引；**禁止**再调用 `delete_asset_record_and_file`。
2. 拍摄组删到剩一张时，现有「降级为单图」可保留，但被移出的那张必须能在回收站恢复（恢复后组关系一期不必完美还原，能回到原文集即可）。
3. 恢复图片：文集仍有效才能恢复；文件还在才能显示。若历史数据已经把文件删了，恢复失败并说明「原文件已不在，无法恢复」。
4. 彻底删除：无其它引用才删文件；有引用则只粉碎 `Image` 行。

### 4.3 白板

1. 恢复：`is_valid=True`，回到白板列表。
2. 彻底删除：物理删除记录 + 墓碑。白板是整板一条记录，没有子资源级联。

### 4.4 通用

- 只有所有者能看见、恢复、粉碎自己的条目
- 不引入独立 TODO

## 5. 界面要点

- 沿用 `/recycle`，不要新开一页
- 列表：标题/文集名/白板名、类型徽标、删除时间；文集行附带下属数量
- 筛选过多时窄屏可横滑，不要把筛选项做成难用的下拉迷宫
- 空状态沿用一期：安全网，不是永久备份
- 危险按钮现有红色体系；主色仍是橘子
- 修正文案的页面：`HomePage` 删文集、`ImageAnthologyPage` 删图、`WhiteboardManagePage` 删白板，以及其它仍写「无法恢复」的同类确认（Markdown 文章/闪念一期已改的不要回退）

## 6. 实现约束（给阿尼亚）

- 复用一期 trash/restore/purge 模式，按领域拆 API（`/anthology/trash`、`/image/trash`、`/whiteboard/trash` 或同等），不要把五种类型塞进一个巨型 view 文件
- 图片删除路径至少包括：`ImageDeleteView`、拍摄组更新里的移除、组级删除。凡是会清文件的，软删阶段都要停
- 粉碎走模型 `delete()` + 现有墓碑；不要只在本机 DROP
- 无新字段则不必改 `TARGET_APPS`、不必升应用版本
- 测试：删文集后文章从目录消失、恢复文集后回来；拒绝无确认粉碎非空文集；删图不删文件、粉碎才删；白板恢复；HTML 笔记仍不出现在回收站

## 7. 验收

- 删除文章文集 → 首页消失，回收站能恢复，原子文章回到目录
- 删除图片文集 / 白板 → 同样能恢复
- 删除单张图片 → 回收站能恢复且图还在；粉碎后文件在无引用时被清理
- 各删除确认不再写「无法恢复」（本范围内）
- 未登录不能访问 `/recycle`
- 不 commit（由人类决定）
