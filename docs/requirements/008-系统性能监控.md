# 系统设置：性能监控实施规划

状态：本地已实现三层采集、页面与报告；目标规格中未落地/未验收项见文末。编制日期：2026-11-06。

本文件保留目标规格与实施顺序；当前行为与验证结果见[系统性能监控说明](../系统性能监控说明.md)，不表示生产已发布或数据库扩展已启用。用户已确认：性能记录、聚合统计与采集阈值均只保留在当前部署，不参与 WebDAV 同步。

## 1. 目标与范围

在「系统设置 → 性能监控」提供统一诊断入口，覆盖三个层次：慢接口、数据库查询、AI 调用与后台任务。管理员能够回答：哪些操作经常慢、慢了多久、主要在哪个阶段、关联哪些 SQL/模型/任务。单条记录可导出自包含诊断包，支持用户交给代码助手分析、定位与修复，并在相同口径下复测。

一期采用项目内采集与页面，复用已有 PostgreSQL，不增加 Redis、Celery 或独立监控平台。保留后续导出到 OpenTelemetry 的边界，一期不实现外部平台对接。

性能监控只负责观测，不改变接口超时、任务重试、模型参数、业务调度和 SQL 执行结果，不自动添加索引或执行 EXPLAIN ANALYZE。接口与任务的内部埋点不改变 Agent 业务规则，因此不新增模型决策步骤。

一期不包含浏览器渲染性能、完整网络耗时、持续 CPU 分析、数据库执行计划自动采样、外部告警推送或服务宕机探测。应用完全不可用时，本页面也不可用。

## 3. 页面与主要操作

仅超级管理员可见和访问，服务端逐接口校验权限。页面沿用白底圆角卡片、橘色强调和胶囊分段控制器。

顶部为时间范围（最近 1 小时、24 小时、7 天、自定义）、模块筛选、手动刷新和「采集设置」。默认最近 24 小时；页面可见时每 30 秒刷新，离开、后台隐藏和请求未完成时暂停，筛选变化取消旧请求。

| 分页 | 主要展示 | 详情与操作 |
| --- | --- | --- |
| 总览 | 请求量、慢请求比例、错误比例、近似 P95、慢 SQL 数、慢模型/任务数；请求量与耗时趋势 | 当前采集状态、最近落盘时间、丢弃量、数据覆盖范围；按累计耗时列出热点 |
| 慢接口 | 按 HTTP 方法和路由模板分组；次数、平均/最大耗时、近似 P95/P99、慢请求比例、SQL 数与累计耗时 | 代表请求详情：请求 ID、耗时阶段时间轴、关联 SQL/AI/外部调用及已有异常日志 |
| 数据库 | 应用采集的 SQL 指纹排行；次数、平均/最大/累计耗时、来源接口/任务 | 安全 SQL 概要、代表慢样本；另设 PostgreSQL 原生统计视图，明确独立口径 |
| AI 与任务 | 内部分为「模型调用」「后台任务」「外部调用」；按模型、任务类型、模块等聚合 | 首次有效输出等待、总耗时、可观测尝试次数、等待/执行时间、阶段明细、关联请求/任务 |

总览按同类指标比较；普通接口、流式响应、AI 和任务不能混成一个慢耗时排行。无首段输出、无排队起点、未知重试次数均显示「未采集/不适用」，不以 0 代替。任务等待业务时间与执行耗时分开。

详情使用弹窗，按时间轴展示已采集的父子阶段。嵌套与并行阶段可能重叠，不把子阶段耗时直接相加或用差值断言 CPU 耗时；未观测区间明确标注。关联异常按请求/调用 ID 查询已有日志，允许日志已过期或不存在。

界面提供暂停采集、修改阈值/保留策略、清空当前部署性能数据（确认弹窗）。单条请求、SQL 执行、模型调用、任务执行及外部调用的详情提供「导出诊断报告」按钮，下载一个 ZIP 诊断包。一期不提供任意 SQL 执行和单条样本删除。

使用统一 `Select.tsx`，弹窗内 `menuPortal={true}`；滚动区隐藏滚动条，详情弹窗接入统一背景滚动锁。窄屏使用紧凑列表，避免整页横向滚动。

### 3.1 单条记录诊断报告

使用流程：打开慢记录 → 查看阶段与采集完整性 → 导出诊断包 → 用户将文件交给代码助手 → 助手核对对应版本源码、区分根因与待验证假设 → 修改并运行相关验证 → 再采集同类记录比较。性能页面不自行调用模型、发送报告或自动修改代码。

导出目标是可定位的具体执行样本。选择子 SQL/模型调用时，报告以该事件为焦点，并携带已保存的父请求/任务和有界兄弟阶段；不混入同一业务任务的其他重试或无关用户请求。聚合行先选择代表样本；若明细已过期或从未保存，明确不能生成单次执行报告，不把聚合统计冒充一条完整调用链。

诊断包默认名为 `performance-<安全记录ID>-<UTC时间>.zip`，包含：

- `report.md`：可直接阅读的中文报告，含定位摘要、事实、线索、对照与限制。
- `evidence.json`：稳定结构的原始诊断证据，含 `reportVersion`、`reportId`、记录/阶段 ID、采集时间、单位、缺失原因和截断标记；与 Markdown 使用同一份安全数据快照生成。
- `manifest.json`：文件列表、SHA-256、导出时间及采集/脱敏规则版本，用于检查包内一致性；校验和不作为来源真实性证明。

报告不依赖仍在线的管理页面或原记录链接即可理解。关联链接可以附加，但 ID、耗时、调用位置和必要异常摘要必须随包携带。报告版本独立于应用版本，后续变更字段时保留兼容读取说明。

| 内容 | 必需证据与边界 |
| --- | --- |
| 记录摘要 | 类型、操作/路由模板、方法、状态、请求/执行/父阶段 ID、发生时间与时区、总耗时、慢阈值及策略版本 |
| 版本与定位 | 发生时应用版本、构建 commit、采集器版本；已部署的 Python/Django/PostgreSQL 版本和实际 worker/thread 配置（仅安全白名单，未知则注明）；导出时版本另列，不能替代发生时版本 |
| 代码位置 | 路由处理器/任务入口的模块与函数；慢 SQL/关键阶段的首个项目调用帧和有界项目调用链，包含仓库相对路径、函数名、行号；不含用户目录、局部变量与源码正文。按样本发生时记录，升级后不能用新行号回填旧事件 |
| 阶段时间轴 | 父子关系、相对起止时间、耗时、并行/包含关系、结果、重试/退避与未观测区间；不能用重叠阶段相加推导总耗时 |
| SQL 证据 | 安全结构模板/指纹、调用次数、累计/最大执行调用耗时、来源帧；同指纹重复次数、代表执行和所在阶段。应用执行与数据库原生统计分别注明来源、时间范围和身份匹配可靠性 |
| 模型/外部调用 | 安全模型标识、首个有效输出类型与等待、总耗时、可见尝试及退避、状态/安全错误分类；输入/输出规模仅限已采集的 token/字符数、响应字节数等数值，不收正文 |
| 工作量与复现线索 | 已实际观测的分页大小、结果数量、批次数、文件大小等白名单规模信息；采集位置和含义固定，缺失则注明。无原始参数、业务正文和数据库快照时，报告不保证可完整重放 |
| 同类基线 | 默认取事件前后各 15 分钟已落盘聚合；按同一路由/任务/模型、同构建版本、同策略版本选择总体；耗时对照另按同类结果筛选，错误率和整体慢比例以全部结果为分母，分别注明范围、样本量、分子/分母与平均/近似 P95；目标事件可能包含在该总体中，不能称为独立正常对照。无可比数据时明确「无基线」 |
| 关联异常 | 通过已采集关联键的指纹只读查询既有 event_correlations；只导出命中聚合的安全分类、聚合 ID、次数与首末时间，标明属于同日同类异常聚合。代表请求/任务/耗时不得视为本次事实；未命中、已过期、读取失败与未采集关联键分别注明，不推断本次无异常 |
| 采集完整性 | 明细截断、丢弃计数的可用范围、缺失阶段、未知重试、版本缺失、数据库扩展状态/重置/缺采、样本与基线是否来自不同保留范围；不把未知值补成零 |

为报告补充的构建身份、安全调用位置、规模和基线版本维度进入本机性能采集与专用模型，不进入业务记录、WebDAV 或业务备份。构建版本作为有界维度；超过维度预算时合并并报告不可精确匹配，而非跨版本强行比较。安全位置只对慢/失败或选定样本保留，有界提取项目帧，验证开销，不为每条快 SQL 保存完整堆栈。

报告中的诊断线索由确定性规则产生，不调用 AI：例如「同一 SQL 模板重复 80 次，累计耗时 1.8 秒」是事实；「检查循环查询或批量预取机会」是建议。相同模板不证明参数相同，不直接判为 N+1；大量 SQL 时间也不证明缺少索引，外部调用慢不能直接归因为本机网络。没有执行计划、锁等待或 CPU 采样证据时，明确对应原因尚未验证。每条线索列出证据 ID、判断依据与下一步核实动作。

导出只读使用已保存数据和必要的安全元数据，不触发业务重跑、模型请求、扩展安装、全表扫描、执行计划采样或远程访问。缺失的索引/执行计划/业务输入作为后续针对性排查项，不能为了导出悄悄补跑请求。若未来补充数据库结构，必须标明是故障发生时还是导出时状态。

服务端以统一安全投影生成 Markdown 与 JSON，防止只对可读报告脱敏却让结构化附件泄露。排除 SQL 参数、提示词、模型回复、业务正文、连接串、认证头、完整 URL/查询参数、用户名/IP/主机路径和运行环境全量转储；业务实体 ID 按既有安全策略转换为包内一致的别名，诊断事件 ID 保留以便本机追查。动态文案转义为文本，文件名与包内路径固定生成。

导出权限与详情相同，响应 `no-store`；支持前端取消、加载和错误处理。一次只导出一个样本及其有界关联，最多 100 个阶段/SQL 明细、20 条关联异常、60 个基线时间桶；解压后全部文件合计不超过 2 MiB，超限优先删减异常堆栈和代表明细，保留摘要与明确的截断清单。首次已截断的采集无法在导出时还原。该上限独立于单样本 64 KiB 的存储上限，不扩大原有采集内容。

先读取目标样本并构造一致的证据快照，随后分源读取基线/日志并标注读取时间与失败原因；附件不能引用不同代次或误称全局事务快照。目标已清理返回明确 404；只有关联数据缺失时仍可导出，报告列出缺口。诊断包即时生成下载，服务端不保存报告副本、不新增导出历史或同步字段；未来若需要报告归档，再单独设计保留策略。

## 4. 第一层：接口采集口径

### 4.1 范围与维度

覆盖进入 Django 的业务 API，包含成功、业务失败和服务端异常。静态资源、健康检查、性能监控 API 自身排除；系统日志查询等诊断流量也排除，避免管理页面刷新污染排行。排除规则以明确路径前缀配置，不能用不受控正则逐请求匹配。

聚合键为方法、Django 路由模板、模块、请求类型、完成状态、策略版本和有界构建身份；资源 ID 不作为聚合维度。无法解析路由的请求按状态归为固定「未匹配路由」，不为每个原始地址建立分组。用户 ID、原始路径、查询参数均不进入指标标签。

普通请求耗时从应用中间件入口到响应对象返回，使用单调时钟；不声称包含代理排队、完整响应传输与浏览器耗时。SQL 用执行次数与累计调用耗时辅助定位，不把网络/锁等待和 Python 处理自动归因为某一原因。

HTTP 5xx 与未处理异常计为接口错误，4xx 单列；任务/模型异常按各自结果计数。主动取消和预期工具结束不计系统错误。一个请求即使含多个模型调用，也只计一次接口请求。

### 4.2 流式响应

分别记录响应对象就绪、服务端首个响应块产出、迭代结束时间；服务端首块不称为用户收到的首字节。同步和异步迭代器均覆盖正常完成、异常、提前关闭和取消，只结算一次。

每次执行迭代器时进入诊断上下文，产出后及时恢复，避免跨 `yield` 遗留线程/协程上下文。生成器不能被预读、缓冲、吞掉结束事件或改变关闭语义。流式请求 SQL 包装必须覆盖迭代执行区间。

流式总耗时单列，不按普通接口 1 秒阈值判断；首块与总耗时分别设置阈值。完成前的长流在在途视图显示，进程崩溃后只能标为结果未知，不能补成成功或精确的执行耗时。

## 5. 第二层：SQL 与 PostgreSQL 统计

### 5.1 应用侧 SQL

使用 Django `connection.execute_wrapper()` 包裹被监控请求/任务实际使用的连接，覆盖 `execute`、`executemany` 的成功和异常。无需打开 `DEBUG` 或长期保留 `connection.queries`。一次 `executemany` 单独记录为一次批量调用，不伪装为已知数量的独立查询。

每个根请求/任务统计 SQL 总次数、累计执行调用耗时、最大单次耗时；每个 SQL 指纹维护聚合指标，超阈值保留有界明细。同一线程/连接只安装一层性能 SQL 包装，嵌套操作复用包装并切换当前阶段；每次实际执行只生成一个 SQL 事件 ID。同一 SQL 同时归属父任务与子阶段时，使用该 ID 避免全局排行重复计数，父阶段的累计值仅表示包含关系。

驱动调用耗时可能含通信及等待，不等同于数据库纯执行时间；游标后续取数和 ORM 构造对象耗时不保证包含在 `execute_wrapper` 中。后台线程的连接独立安装包装，不能认为主请求的包装自动覆盖子线程。

SQL 文本只允许保存经 PostgreSQL 语法/词法分析后去除字面量、参数和注释的结构模板。覆盖美元引用、字符串、数字、批量值和工具语句；不能仅靠正则删除引号。无法可靠规范化时只保留不可逆指纹、语句类型、耗时和安全调用位置，并注明「SQL 概要未采集」。在进入队列前完成安全投影，原始 SQL、参数不落盘。

### 5.2 PostgreSQL 原生统计

提供 `pg_stat_statements` 能力检测与只读排行，展示 calls、mean/max/total_exec_time、rows 等可用字段；不为页面展示授予超级管理员数据库权限，权限不足给出明确状态。

原生统计是数据库累计快照，不能直接套用页面「最近 1 小时」。后台定期采集快照并在相邻有效采样间求差，按完整采样区间筛选；平均耗时由总耗时差/次数差计算，区间最大耗时不可从累计最大值相减得出。首次快照、计数下降、统计重置、数据库重启或指纹淘汰时，重新建立基线并标记缺口，不产生负数。保留累计视图供核对。

默认每 60 秒采样；以当前部署数据库实例身份、dbid、userid、queryid、toplevel 组成可用的稳定键，记录扩展重置时间、重启边界及可用的淘汰计数。缺行后重现不与旧行直接求差；淘汰计数变化且无法证明连续时，相应区间标为缺口。缺采间隔超过 120 秒时不连接成连续区间；更短的延迟明确标注实际采样间隔，不插值为分钟数据。

每次最多保存累计总执行耗时前 1,000 个指纹，记录选择规则与截断状态。原生排行只代表已采样集合，不声称覆盖数据库全部 SQL；跨采样未持续入选的指纹重新建立基线。实施时根据实际 PostgreSQL 版本复核可用身份/重置字段，缺少可靠身份的区间不计算差值。

原生视图与应用侧排行不合并计数：前者覆盖数据库所见语句，后者可以关联项目请求/任务，二者耗时边界不同。原生统计仍会包含监控自身的数据库操作；当前不读取原生 SQL 文本，不擅自识别或隐藏监控语句；页面说明原生统计包含监控流量，不声称应用侧排除上下文能阻止数据库统计。原生 SQL 文本经过相同安全投影，不能假设扩展返回内容天然无敏感值。

应用上线不自动执行 `ALTER SYSTEM`、重启数据库或重置统计。部署步骤为：核对已有 `shared_preload_libraries` 并保留现有项 → 加入扩展 → 安排数据库重启 → 在目标库安装扩展 → 验证最小读取权限与采样。扩展未启用时显示「未启用」，应用侧 SQL 仍正常工作；一期完整验收另需完成原生统计验收。

## 6. 第三层：AI、任务与外部调用

### 6.1 AI 口径

逻辑调用保留独立调用 ID、父操作 ID、安全模型标识、提供商、开始/结束时间、首次有效内容或思考/工具增量时间、结果类别。首次网络块、心跳/空块不算有效模型输出；不同首输出类型在详情注明。

逻辑调用包含应用可见的重试与退避，实际尝试作为子阶段单列。SDK 内部未暴露的尝试数显示未知，不能用配置的重试上限当实际次数。`model_operation` 与 `bounded_completion` 重叠路径只产生一个逻辑调用统计，尝试和外部 HTTP 不能再次计为逻辑调用。

非流式模型记录总耗时，首输出不适用。主动取消、预期工具结束、超时、失败、结果未知区分；生图提交耗时、轮询 HTTP 耗时与服务商生成等待时间分开，不能把一次提交成功当生成完成。

### 6.2 后台任务口径

任务提交、实际开始和结束分别记录。只有存在真实提交/可运行时刻才计算排队等待；预约执行时间尚未到、业务准备时间或资源预留等待不混成调度器排队。

首次执行、重试与恢复各有执行 ID，关联同一个业务任务 ID；轮询心跳和租约续约不计为新任务。暂停等待不持续占用执行计时；只能观测到整段函数时明确展示该边界。跨线程显式传播父 ID，子线程使用独立上下文。

### 6.3 一期接入清单

| 范围 | 已定位入口 | 交付要求 |

## 7. 默认策略与统计算法

以下是一期初始值，均为本机策略，可按实际数据调整，不是业务超时或故障判定。

| 指标 | 初始慢阈值 |
| --- | --- |
| 普通接口 | ≥ 1,000 ms |
| 单次 SQL 执行调用 | ≥ 200 ms |
| 单次请求/任务 SQL 累计调用耗时 | ≥ 500 ms |
| 单次请求/任务 SQL 调用数 | ≥ 50 次，显示「查询次数偏多」，不直接判定 N+1 |
| 流式接口首块 / 总时长 | ≥ 5,000 / 120,000 ms，独立分类 |
| AI 首次有效输出 / 逻辑调用总时长 | ≥ 10,000 / 60,000 ms，模型可覆盖默认值 |
| 后台任务执行 | ≥ 60,000 ms，任务类型可覆盖；等待时间单独展示 |
| 外部调用 | ≥ 3,000 ms，流式模型 HTTP 与普通 HTTP 分组 |

普通请求、SQL、AI、任务均做全量轻量聚合，明细只保留慢操作、失败和少量正常代表样本。这里的「全量」指符合采集范围且未丢失的事件，不承诺故障期间完整。操作结束时使用该 worker 已加载的策略版本判断慢阈值，并在事件与聚合中记录版本；不同版本的慢比例分开展示。策略保存后有最长一个刷写周期的传播窗口，页面展示保存时间、预计生效窗口和各 worker 最后确认版本，不暗示保存瞬间所有操作已切换；失联 worker 的状态标为未知。

每分钟聚合次数、错误数、慢次数、耗时总和/最大值和固定桶计数。P95/P99 从可合并的直方图估算，禁止平均各分钟或各进程的 P95。建议毫秒桶上界：1、2、5、10、20、50、100、200、500、1000、2000、5000、10000、30000、60000、120000、300000、600000、1800000、+∞；跨进程固定同一桶版本。页面标明「近似」及所属桶范围，溢出桶显示下界，不伪造精确值。

一期时间筛选按完整分钟桶，返回实际生效起止范围；详情样本按精确时间筛选，明确二者可能在边界不同。数据库保存 UTC，按系统展示时区显示。

SQL/路由/任务维度设置数量上限；超限进入固定「其他」分组并显示合并数量。每个根操作明细最多 100 个子事件、样本大小上限 64 KiB，截断时保留计数与截断标记。禁止无限收集堆栈、SQL 或生成内容。

## 8. 存储、并发和同步边界

### 8.1 模块与数据

新增 Django app `system_performance`。专用 PostgreSQL 表由 migrations 管理，与业务表分开；复用现有数据库持久化卷，不新建磁盘 SQLite。

拟定模型职责（具体字段在实施时落实）：

- `PerformancePolicy`：单例本机策略、版本和清空代次。
- `PerformanceBucket`：时间桶、聚合键、计数、耗时、直方图；合成唯一约束。
- `PerformanceSample`：根操作及有界子事件、安全 SQL 概要、关联 ID、发生时构建身份/代码位置/安全规模信息与截断标记，支持离线诊断报告。
- `PerformanceInflight`：超长在途操作的限频心跳与过期标记；只辅助诊断，未知结束不当成功。
- `DatabaseStatSnapshot`：数据库统计快照、重置标识及采样区间。
- `PerformanceFlushBatch`：批次去重凭据与过期时间，防止提交结果未知时重试重复聚合。

全体模型加入 `LOCAL_ONLY_MODEL_LABELS`；确认同步导出、修订跟踪、恢复与用户主动业务备份的实际选模都排除它们。旧备份恢复不能清空或覆盖本机策略。直接整库 `pg_dump`/卷快照会包含这些表，这与 WebDAV/业务备份排除是不同边界，部署说明需写明。

建议明细保留 7 天，分钟统计保留 30 天；原生快照保留 7 天，在途记录结束/过期后短期清理。默认 200 MiB 为活跃性能数据的保守估算预算：JSON 文本字节两倍，加每行 2 KiB 开销预留，覆盖样本、桶、快照、在途与批次凭据。共享计量保存在本机策略 JSON，与数据写入在同一策略行锁事务内预留和更新，首次及维护时仅对性能表重新核对。先为聚合和去重凭据预留空间，余量用于明细；不足时限制样本，必要时跳过整个新批次并计数，快照和在途新增同样受控。压力下持续分批按时间清理，低于约 85% 后恢复明细，单轮清理有时间限制。24 小时内的去重凭据不得为了腾空间提前删除；受保护记录已高于下调后的预算时保持限流。该预算不是数据库物理文件硬上限，不包含 PostgreSQL 共享 WAL/备份空间，空页与索引回收有滞后。快照清理导致无法连续求差时标记缺口。

### 8.2 写入与生命周期

各 worker fork 后惰性启动本进程采集器，线程使用独立诊断上下文。请求路径只做计时、有界聚合和入队，不逐事件同步落库。初始队列上限 2,048 条且序列化负载合计不超过 8 MiB、低流量约每 5 秒刷写，达到 200 条唤醒，有积压则连续批量刷写；聚合缓冲预算 4 MiB，另设维度上限。任一上限触发即按明确策略合并/丢弃并计数，实际 Python 对象开销另行实测，不能只限制明细条数。

批次用唯一 ID 在同一事务中登记、原子累加统计并写明细；同批重试不重复计数。初始批次去重凭据保留 24 小时，重试窗口不超过 5 分钟且次数有上限；超窗丢弃，禁止在去重凭据过期后重放。跨进程并发合并使用数据库原子更新，禁止先读后写覆盖直方图。进程收到退出信号时有界刷写；强杀、OOM 和断电可丢失尚未落盘的数据。

监控连接及业务事务隔离，业务事务回滚不回滚已观测的失败；监控写入设连接/锁/语句超时，失败限次重试与退避后丢弃，不阻塞业务。监控库故障与主库故障可能同时发生，内存状态只能尽力报告，不能保证恢复崩溃进程的丢失量。

首次安装默认暂停采集，管理员在本机页面开启；后续部署保留已保存策略。策略/表结构不可用时关闭采集并显示原因，不能影响业务启动。采集暂停、阈值修改跨 worker 在一个刷写周期内生效。清空采用新代次；写入时拒绝旧代次批次，防止清空后旧队列重新填回历史。清空保留策略与必要健康元数据；清理/快照采样只有一个持有租约的执行者，支持过期接管。

监控表写入、采样和 API 查询设置显式排除上下文，避免采集自身 SQL、递归异常与无休止写入。仅采集必要信息；存储失败使用限频安全日志，不回显原始事件。

接口前缀拟为 `/api/system/performance/`，沿用成功/错误契约、HTTP 状态码和 camelCase 转换，全接口管理员校验、禁止缓存。

前端拟新增 `components/Settings/PerformanceMonitor/`、`hooks/usePerformanceMonitor.ts`、`api/performance.ts`、`types/performance.ts`；设置页只注册入口和编排。新增有类型 local mock，接入实际 mock 路由分派入口，包含所有列表、详情、策略、清空、能力检测与诊断包下载请求，下载用例提供能实际解压的 ZIP。图表优先复用现有图表组件/依赖。

## 11. 验收清单

1. **接口**：快/慢成功、4xx/5xx、未处理异常、未知路由、资源 ID 不增维；每个根请求只统计一次。流式同步/异步正常、异常、关闭与取消后原始返回值和事件顺序保持一致。
2. **SQL**：单条慢 SQL、50 次快查询、累计慢、批量调用和失败 SQL；请求/任务连接隔离、子阶段去重；监控查询不进入排行；游标取数边界在详情可见。
3. **敏感信息**：用测试用的唯一标记覆盖 SQL 字面量/注释/美元引用、认证头、模型正文和完整 URL，检查队列、数据库、接口和日志均无原文；规范化失败关闭文本采集。
4. **AI/任务**：非流式、首个有效增量、空块、工具调用、可见重试、SDK 未知重试、预期结束、取消/超时、提交/轮询和恢复；排队时间缺测显示未知，父子计数不重叠。
5. **统计与故障**：人工构造分布验证跨分钟/跨进程百分位、慢比例及阈值版本；检查队列满、数据库不可用、锁竞争、提交结果未知、worker 重启、清空代次、策略传播和容量清理。
6. **原生统计**：未启用/权限不足不误报为零慢 SQL；快照差值、首次采样、统计重置、重启、指纹淘汰以及累计最大值边界均可解释。
7. **同步与权限**：新增模型不进入修订、WebDAV、业务备份/恢复；普通用户和匿名用户无法读写，直接请求详情也拒绝；性能功能关闭不影响业务。
8. **前端**：Node 22 下相关测试、type-check 与构建；`sh dev.sh local` 检查正常/空/加载/错误、详情、策略、清空和能力缺失，无 501、无真实后端请求；桌面/窄屏与弹窗、轮询清理、旧请求覆盖验证。
9. **开销**：在隔离 PostgreSQL/测试数据上，对同一负载比较关闭/开启的请求延迟、CPU、内存和写入量。以普通接口 P95 增幅 ≤5%、进程新增常驻内存 ≤30 MiB 为初始目标，记录硬件、并发、样本量与误差；不满足时优化或明确调整预算，不能用 local mock 证明性能开销。
10. **诊断报告**：构造重复 SQL、单条慢 SQL、慢模型、任务等待与阶段缺测样本；解压后核对 Markdown/JSON 事实、单位、ID 和校验和一致，版本是发生时版本，无法得出的根因不下定论。验证跨部署版本、无基线、记录已清理、关联日志缺失、阶段/包体截断、并发清空、取消下载和权限失败。用同一测试敏感标记扫描所有附件；前端 local 下载必须得到真实 ZIP，无真实后端请求。离线仅凭诊断包能定位到测试用例的代码入口与已知瓶颈；复测对照注明版本、数据规模、并发、采集策略和样本量，未知业务状态不能宣称精确复现或已证明优化有效。

数据库相关命令严格遵守根目录 AGENTS：先确认已有 PostgreSQL 容器与配置，再显式加载连接；不回退 SQLite。测试不得访问现有业务数据或启动真实后台调度器。若测试需要隔离测试库，先落实现有授权与环境，不擅自创建替代数据库。

## 12. 上线与停用

迁移、启用采集和 PostgreSQL 扩展配置分别执行与验证。先在测试环境对照，再在生产启用聚合与有限样本；页面展示启用时间，历史不能追补。上线记录说明实际启用路径、扩展状态、采集开销与尚未验证项。

需要停用时关闭性能采集并停止写入/轮询，业务继续运行；已有性能表可保留供排查。不自动删除数据或卸载数据库扩展，数据库 preload 回退如需重启应单独安排。外部宕机告警和成熟监控平台对接留待后续需求。
