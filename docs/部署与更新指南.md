# O-Doc 部署与更新指南

这份文档把 O-Doc 的发布方式固定成一条简单链路：

1. 代码提交到 GitHub。
2. GitHub Actions 自动构建 Docker 镜像并推送到 GHCR。
3. 服务器执行 `docker compose pull && docker compose up -d` 获取最新版本。
4. 通过 `scripts/deploy.sh` 脚本完成首次安装、后续更新和卸载。

这样做的核心好处是：发布时不再依赖本地手工执行 `update.sh`，服务器也不需要自己编译前端。

## 1. 最终发布方式

项目现在推荐采用“开发和发布分离”的方式：

- 开发环境：前后端分别启动，前端改动不需要每次构建镜像。
- 生产环境：只认 Docker 镜像，不认本地构建结果。

镜像内部会自动完成这些事：

- 用 Node 构建 `frontend_react`
- 把前端构建产物拷贝到 Django 的 `templates/` 和 `static/`
- 启动容器时执行 `migrate`、`collectstatic`
- 启动 Gunicorn 服务

## 2. 本地开发流程

本地开发时使用项目根目录的 `dev.sh`：

```bash
./dev.sh
```

脚本会同时启动两个服务：

- 后端 Django：`http://localhost:11800`
- 前端 Vite：`http://localhost:5173`

日常开发请访问 `http://localhost:5173`。这是 Vite 开发服务器，会读取 `frontend_react/src` 下的最新代码，并把 `/api`、`/media` 请求代理到 `http://localhost:11800`。

不要用 `http://localhost:11800` 验证前端开发改动。`11800` 是 Django 后端入口，它渲染的是 `templates/index.html` 和 `static/` 里的已构建前端产物；`dev.sh` 不会自动执行前端 build，也不会把构建结果复制到 Django 模板和静态目录。

如果确实需要让 `11800` 看到最新前端，需要手动执行：

```bash
./update.sh
```

`update.sh` 会执行 `frontend_react` 的生产构建，并把 `dist` 产物复制到 Django 的 `templates/` 和 `static/`。这个流程适合验证一体化静态产物，不是日常前端开发的默认入口。

### 2.1 Mock 数据开关

前端的 MSW Mock 默认关闭，避免开发联调时拦截真实后端接口。

默认开发方式：

```bash
./dev.sh
```

此时访问 `http://localhost:5173` 会走真实后端接口。

如果只想看纯前端静态演示数据，可以显式开启 Mock：

```bash
VITE_ENABLE_MOCKS=true ./dev.sh
```

或者单独启动前端：

```bash
cd frontend_react
VITE_ENABLE_MOCKS=true npm run dev
```

开启 Mock 后，`frontend_react/src/mocks/handlers.ts` 中定义过的接口会返回模拟数据；未定义的请求仍会按 Vite 配置代理到后端。

## 3. 你需要知道的几个概念

### GitHub Actions 是什么

GitHub Actions 是 GitHub 自带的自动化工具。你可以把它理解成：

- 你往仓库推一次代码
- GitHub 在云端开一台临时机器
- 按你写好的流程自动执行命令
- 这里我们让它自动构建 Docker 镜像，并推送到镜像仓库

你之前以为镜像必须在本地打包，这其实不是必须的。只要仓库里有 `Dockerfile`，GitHub Actions 就可以直接在 GitHub 的机器上构建镜像。

官方参考：

- [GitHub Actions 发布 Docker 镜像](https://docs.github.com/actions/tutorials/publish-packages/publish-docker-images)
- [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)

### GHCR 是什么

GHCR 是 GitHub Container Registry，也就是 GitHub 自家的 Docker 镜像仓库。

你可以把它理解成：

- GitHub 仓库存源码
- GHCR 存构建好的镜像

例如镜像名一般会长这样：

```text
ghcr.io/<你的 GitHub 用户名或组织名>/o-doc:latest
```

## 5. 第一次使用 GitHub Actions

### 5.1 默认会在什么时候触发

当前工作流配置为：

- 当你 push 一个以 `v` 开头的 Git tag（例如 `v0.9.3`）时自动触发
- 也可以在 GitHub 网页上手动触发一次

`master` 分支本身的普通 push 不会触发当前的镜像发布工作流。发布前应先把待发布代码推到 `master`，再创建并推送对应 tag。

文件位置：
[../.github/workflows/docker-image.yml](../.github/workflows/docker-image.yml)

### 5.2 你第一次需要做什么

1. 把这次改动提交到 GitHub 仓库。
2. 确保默认发布分支是 `master`。
3. 打开 GitHub 仓库页面。
4. 进入 `Actions` 页面，确认 `Build And Publish Docker Image` 工作流成功执行。
5. 执行成功后，到仓库右侧的 `Packages` 或个人/组织的 `Packages` 页面查看镜像。

### 5.3 如果你的默认分支不是 `master`

把工作流里的：

```yaml
branches:
  - master
```

改成你的实际发布分支，比如 `main`。

### 5.4 GITHUB_TOKEN 要不要自己配

这套流程默认直接使用 GitHub 自动提供的 `GITHUB_TOKEN`。

通常不需要你额外创建 Docker 仓库密码。关键点是工作流里已经声明了：

```yaml
permissions:
  contents: read
  packages: write
```

这表示当前工作流有权限把镜像推送到 GHCR。

## 6. 服务器首次部署

下面以 Linux 服务器为例。

### 6.1 安装 Docker 和 Docker Compose

先确保服务器有：

- Docker
- Docker Compose

如果执行下面命令都正常，就说明环境没问题：

```bash
docker --version
docker compose version
```

### 6.2 在服务器上拉一份仓库

服务器只需要保留一份仓库，用来保存这些部署文件。通过 `scripts/deploy.sh` 启动时，实际部署目录是仓库下的 `deploy/`；如果直接运行 `manager.sh`，实际部署目录默认是 `$HOME/o-doc`。

- `<部署目录>/compose.prod.yml`
- `<部署目录>/.env`
- `scripts/deploy.sh`
- `<部署目录>/runtime/` 数据目录

示例：

```bash
git clone <你的仓库地址>
cd O-Doc
```

### 6.3 创建部署环境变量文件

第一次执行脚本时，如果部署目录里没有 `.env`，脚本会自动生成一份，并提醒你修改。旧版部署里的 `.env.deploy` 会被脚本自动迁移为 `.env`。

如果使用仓库里的 `scripts/deploy.sh`，也可以手动先复制：

```bash
mkdir -p deploy
cp .env.deploy.example deploy/.env
```

如果是直接运行 `manager.sh`，则把 `.env` 放在 `compose.prod.yml` 同级目录即可。

然后重点修改这几个值：

```bash
IMAGE_NAME=ghcr.io/<你的 GitHub 用户名或组织名>/o-doc:latest
DJANGO_SECRET_KEY=改成一段足够长的随机字符串
DJANGO_ALLOWED_HOSTS=你的域名,你的服务器IP
HOST_PORT=11800
ADMIN_EMAIL=你的管理员邮箱
```

注意：

- `DJANGO_SECRET_KEY` 在生产配置里是必填项
- 当 `DJANGO_DEBUG=false` 时，如果没有设置 `DJANGO_SECRET_KEY`，容器会直接启动失败

### 6.4 如果镜像是私有的

先在服务器登录 GHCR：

```bash
echo <你的 GitHub PAT> | docker login ghcr.io -u <你的 GitHub 用户名> --password-stdin
```

这个 PAT 至少需要读取 packages 的权限。

如果镜像是公开的，通常不登录也可以拉取。

### 6.5 执行首次安装

```bash
chmod +x scripts/deploy.sh
./scripts/deploy.sh install
```

或者直接执行交互菜单：

```bash
./scripts/deploy.sh
```

首次安装会做这些事：

- 创建本地数据目录
- 拉取 GHCR 上的最新镜像
- 启动容器

## 7. 后续怎么更新

以后你的更新流程就固定成下面两步：

1. 本地改代码并推送到 GitHub。
2. 等 GitHub Actions 把新镜像构建完成后，在服务器执行更新脚本。

更新命令：

```bash
./scripts/deploy.sh update
```

它本质上就是执行：

```bash
cd deploy
docker compose --env-file .env -f compose.prod.yml pull
docker compose --env-file .env -f compose.prod.yml up -d
```

如果你是直接运行 `manager.sh` 的独立部署目录，同样是在 `compose.prod.yml` 同级目录执行上面的两条 `docker compose` 命令，不需要额外的 `deploy/` 前缀。

如果你隔很久回来忘了命令，直接运行：

```bash
./scripts/deploy.sh
```

按菜单选就行，主菜单里会直接给出：

- `安装`
- `更新`
- `卸载`

## 8. 脚本支持的命令

```bash
./scripts/deploy.sh install
./scripts/deploy.sh update
./scripts/deploy.sh uninstall
./scripts/deploy.sh status
```

说明如下：

- `install`：首次部署，也可以重复执行
- `update`：拉最新镜像并重建容器
- `uninstall`：停止并删除容器，可选是否删除本地持久化数据
- `status`：查看容器状态

## 9. 发布、镜像与服务器更新的关系

当前发布链路如下：

```text
提交并 push master
        ↓
创建/推送 vX.Y.Z tag
        ↓
GitHub Actions 构建新镜像并推送
        ↓
腾讯云 TCR 的 o-doc:latest 被新镜像覆盖
        ↓
服务器执行 manager.sh「更新」或 deploy.sh update，拉取 latest 并重启
```

### 9.1 腾讯云镜像的 tag 规则

工作流中的自托管打包机推送的是腾讯云 TCR 镜像：

```text
ccr.ccs.tencentyun.com/tangerine_specter/o-doc:latest
```

目前腾讯云只推送 `latest`，**不会**推送 `v0.9.3` 这类版本 tag。因此，服务器更新时拉取的是 `latest`；只要对应 Action 已成功，`latest` 的内容就是最新发布 tag 所指向的代码。

即使打包机或腾讯云仓库中已有旧的镜像，新的 Action 仍会重新构建并把同一个 `latest` tag 指向新镜像。一般不需要先删除腾讯云的旧镜像，也不需要在服务器手动删除旧镜像。

GHCR 会额外拥有 Git tag 对应的镜像 tag（例如 `v0.9.3`）以及 commit SHA tag；这与腾讯云 TCR 的 `latest` 策略不同。

### 9.2 服务器如何获取新版本

先确认 GitHub Actions 中新的一次 `Build And Publish Docker Image` 已成功，尤其是 `Publish Tencent Cloud TCR`。随后在部署服务器运行：

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/TangerineSpecter/O-Doc/master/manager.sh)"
```

在菜单中选择“更新”。脚本会保留当前 `.env` 中的 `IMAGE_NAME`，执行 `docker compose pull` 后重启容器。

如果部署使用腾讯云源，`IMAGE_NAME` 应为：

```text
ccr.ccs.tencentyun.com/tangerine_specter/o-doc:latest
```

如果使用 GHCR 源，则会拉取 `.env` 中配置的 GHCR `latest`。无论使用哪个源，都应在对应 Action 成功后再更新；不要用部署脚本去拉取并不存在的腾讯云 `v0.9.3` 镜像。

### 9.3 版本号或 tag 推错时的自救流程

例如：代码里误把版本写成了 `0.10.0`，却已打并推送了 `v0.9.3`。修正版本号后，按下面顺序操作：

```bash
git add frontend_react/package.json
git commit -m "chore: correct version to 0.9.3"
git push origin master

git tag -fa v0.9.3 -m "Release v0.9.3"
git push origin v0.9.3 --force
```

这会把已有的 `v0.9.3` tag 移到修正版本号后的新提交，并触发一轮新的镜像发布。这里的 `--force` 是有意为之：远端 tag 已存在时，只有强制推送才能更新它。执行前务必确认 tag 名和目标版本正确，因为其他已拉取该 tag 的人需要同步更新本地引用。

不要直接在旧的 Action 运行记录里点击 “Re-run jobs”。旧运行仍对应打错版本号时的提交。应等待强推 tag 后自动创建的新运行；如果没有自动创建，在 `Build And Publish Docker Image` 页面点击 “Run workflow”，并选择 `v0.9.3`。

如果误推的 `0.10.0` 镜像 tag 已经出现在 GHCR，它只是多余的历史镜像，不会妨碍正确的 `v0.9.3` 和腾讯云 `latest` 发布，可在确认新版本运行正常后再按需清理。

## 10. 数据放在哪里

为了避免容器更新后数据丢失，当前 compose 文件已经把数据挂到宿主机目录：

- `./deploy/runtime/postgres`
- `./deploy/runtime/media`
- `./deploy/runtime/chroma_data`

也就是说：

- PostgreSQL 数据库文件会保存在宿主机
- 上传文件会保存在宿主机
- ChromaDB 向量数据会保存在宿主机

这样即使你重新拉镜像并重建容器，数据也还在。

## 11. 以后如果要改部署配置

日常业务代码更新只需要：

```bash
./scripts/deploy.sh update
```

但如果你后面改了这些基础部署文件：

- `compose.prod.yml`
- `scripts/deploy.sh`
- `.env.deploy.example`

那服务器上的仓库也要记得同步一次：

```bash
git pull
```

然后再执行：

```bash
./scripts/deploy.sh update
```

## 12. 常见问题

### 12.1 为什么服务器不用再本地构建前端

因为前端构建已经放进 Dockerfile 里了，构建镜像时会自动完成。

### 12.2 为什么还要在服务器保留一份仓库

不是为了在服务器编译代码，而是为了保留部署配置、环境变量模板和更新脚本。

### 12.3 如果 GitHub Actions 失败怎么办

先去 GitHub 仓库的 `Actions` 页面看失败日志。常见原因通常是：

- `Dockerfile` 构建失败
- 依赖安装失败
- 分支名配置不对
- 仓库权限不对，无法写入 GHCR

### 12.4 我能不能以后做成全自动

可以。等你这套半自动流程跑顺以后，再把服务器更新动作接成自动触发就行。但你现在先用半自动是非常稳妥的，出问题也更好排查。
