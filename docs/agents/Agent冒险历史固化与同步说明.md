# Agent 冒险历史固化与同步

> 本文描述当前代码中的历史固化、后台统计和七天回合清理；规则版本、装备、成长、冒险与同步入口见[迷宫探索与战斗说明](./Agent迷宫探索与战斗说明.md)。旧版按检查点删除事实的入口已停用；本次实现和验证不代表用户环境已发布或回填完成。

## 运行数据与历史记录

- 当前角色使用当前运行目录。新规则包首次启动安装时，空闲居民更新到新目录；未结束冒险的居民继续使用出发时规则，结束后再更新。
- 装备的实际属性、名称、词条和价值仍使用原 `EquipmentInstance.snapshot`，不重新生成、不按新版模板重抽。新增的 `rules` 保存独立穿戴条件：格式版本、部位、装备类型、握持方式及各职业最低允许等级。
- 装备生成时固化穿戴条件；旧装备升级时从原目录一次性补齐。之后穿戴、换装、转职检查、出发校验和同步均读取固化条件，不再查装备来源目录。
- 已结束冒险的 `snapshot.history` 保存格式版本、原目录编号、地点与职业标签，`history_frozen=1` 标记已固化。消耗、掉落、成长、遭遇、战报继续使用已保存的事实和结果。
- `catalog_id` 保留为来源说明，不要求旧装备或已结束冒险的目录在数据库/同步快照中仍存在。未结束冒险和当前居民仍需相应运行目录。

## 固化检查点

旧居民第一次升级时，在同一事务中检查原事实链哈希连续性、聚合状态指纹、账号归属和战斗库存收支，再追加 `checkpoint` 事实。检查失败会回滚，不会把损坏数据自动认定为合法历史。

检查点保存原链终点、原聚合指纹、当前成长、已有装备属性与穿戴条件、战斗库存余额。旧流水账原文和哈希不改写；新记录接在检查点后。固化接受已保存的结果作为历史权威，不再用旧版生成器、转职或成长公式重算。

后续升级、转职、目录切换和击杀记录保存 `progression_after`；生成装备的记录保存 `equipment_after`。跨居民交易同时记录装备属性与穿戴条件。同步检查这些固化结果、装备来源、归属转移、库存收支和最终聚合指纹，而不是重放历代规则。

2026-10-26 曾支持按检查点边界归档旧事实（见下节），现已停用该实际删除入口。新的七天清理只移除符合条件的逐回合过程，使用结算和链区间继续核验；检查点解除的是历史规则依赖，不应手工删除事实。

### 跨领域材料收支（2026-10-22）

战斗库存数量按保留的事实链（归档时为 `CombatIntegrity.archive_stock` 加留存事实），以及同居民、同账号的市场交易与炼金制作记录共同核对。材料挂牌扣除背包余额、购买增加买方余额、撤回（含居民归档下架）返还卖方余额，炼金按制作快照的材料明细扣除；挂牌托管不重复算入背包。数量核对不重跑历史规则或重新扣库存，检查点之前的交易也只统计一次。首次固化同样携带这些来源，支持先买材料后首次建立战斗档案。

此前只计算战斗掉落、药剂和商店回收，合法挂牌或炼金后也会报「战斗库存与消费、掉落事实不一致」。手动强制上传先构建安全快照，因此也会触发这一误报。修正来源核对后，正常上传、覆盖和恢复沿用相同校验；缺少收支事实、数量不符或账号串用仍拒绝。无新增持久字段、迁移或同步协议；全部同步设备应更新修复代码。回归入口为 `combat/test_stock_sync.py`，真实双设备 WebDAV 尚待验收。

## 启动、同步与兼容

- 数据库迁移：`0077_equipment_frozen_rules` 新增装备 `rules` JSON 字段。先按既有升级流程备份并执行迁移，后端启动安装规则时自动固化旧数据，重复启动不会重复建立检查点。
- 固化与空闲居民目录更新在共享同步锁和事务中完成。原装备属性、已确认结果和历史流水不回写；无关的生活、市场和美食数据继续使用原事实。
- WebDAV 战斗协议升至8，新增 `combat_checkpoints`、`combat_catalogs`、`combat_current_catalog` 清单；固化字段和检查点完整同步，不设置可独立关闭的同步开关。
- 导出仅携带最新目录、居民当前运行目录和未结束冒险所需目录。无运行引用的旧目录在普通运行时保留本机，但不再随全量快照重复导出；整库恢复仍遵循快照原有覆盖语义。
- 旧版0～7快照先在内存核验并固化，再进入正常恢复。此时仍需要旧快照里的原目录来补齐穿戴条件；缺失依据时拒绝恢复，不凭新版规则猜测。完成转换后导出新版快照即可摆脱该依赖。
- 新版快照必须具有完整检查点、装备穿戴条件和聚合指纹。修复/放宽完整性模式也不能跳过这些核心检查；旧回顾文案可以沿用已有归一流程。
- 恢复事实流作为居民聚合的一部分原子替换，避免新增检查点导致序号唯一约束冲突；重复恢复不会新增奖励、重新消费或重复固化。
- 不改变本机授权、租约、自动运行开关和跨设备接续限制。所有参与同步的设备应升级后再交换协议8快照。

## 旧战斗事实归档与回填保护

- 旧版归档以检查点为边界，删除边界之前的个人事实，包括出发等非回合事实；被删事实的物资净变化保存在 `archive_stock`，链从 `archive_digest` 继续校验。组队个人奖励、武道大会奖品和打造来源若落在待删范围则跳过，故不能满足按场次只清理七天以前回合的目标。
- 当前代码停用旧版自动和手动实际删除，即使 `ODOC_COMBAT_ARCHIVE_DAYS` 显式为正数也不会执行；保留 `archive_combat_facts --days 7` 只读预览和手动检查点命令，`--apply` 返回错误。已有旧实例在更新前仍遵循自身配置。新的七天清理由后台独立处理，不写逐回合删除墓碑。
- 2026-11-02 本地新增回填保护开关 `ODOC_COMBAT_BACKFILL_PROTECT=1`：本版进程进一步暂停快照写入、同步覆盖和恢复；只读归档预览仍可用。默认未开启，无法识别的配置值按开启保护处理，并在日志及被拦截的同步中明确提示配置异常。此开关是每个进程的本机运行配置，不新增持久字段或 WebDAV 同步项；迁移前仍需停止或隔离不认识该开关的旧设备，并在所有实例配置并核验。保护本身不生成统计汇总，也未替代七天清理方案；线上部署状态应另行核对。
- 本版 `python manage.py inventory_combat_backfill [--owner 账号]` 只读盘点账号的探索状态、个人及共享事实数量和旧归档边界，不读取回合 JSON 或删除数据。超过七天的结束探索数量只是初步观察，尚未校验共享依赖、来源完整性或远端状态，不能当作可删除数量；输出中的保护状态仅反映命令进程，不能代替对应用进程和其他设备的核验。
- `python manage.py preview_party_retention --owner 账号 --party 共同冒险ID` 只读检查最后一位成员的实际结束与离队时间、贡献和本机回合数量。尚有原始来源时会临时重建结算；已清理场次读取压缩结算并标明 `archived`。预览不授权删除：后台事务还需检查全部已结束战斗、完整事实链、资产及压缩后的恢复数据。PostgreSQL 的载荷字节只覆盖回合 JSON 列，不含整行、索引、碎片和备份，不能当作可释放空间。
- `python manage.py preview_party_daily --owner 账号 --party 共同冒险ID` 只读预览一场已结束会话的上海日期击杀贡献，按魔物及实际参与的个人探索聚合，世界击杀不会因多人参与重复计数。它核对共同事件链、波次及个人回执，并为来源和时间生成指纹；不核验完整个人链、资产或远端来源，因此不写入汇总，也不能作为清理依据。预览持本机农场／同步互斥锁并限制来源行数（默认 20000，最多 50000），较大会话会被拒绝而不是无限读取。
- 本地迁移 `0098_combat_party_daily` 新增 `CombatPartyCoverage` 与 `CombatPartyDay`；`backfill_party_daily --owner 账号 --party 共同冒险ID --apply` 在本进程开启回填保护时校验个人事实链、状态指纹和共同来源，再幂等写入这些可同步的贡献。`backfill_party_daily_batch [--owner 账号] [--after 游标]` 可分页处理，返回失败原因与下一游标；每批一个事务、每场一个保存点，同批已核验的个人链持锁并复用。单场来源格式异常时记录失败并继续其他场次，失败场次不写摘要或删除来源；批次异常终止则整批回滚。个人链和历史状态流式核验，以既有算法校验全部事实，不把整条历史载入内存。单场来源默认限 20000 行、最多 50000 行；本批尚未核验的居民链和状态合计默认限 500000 行，可用 `--max-actor-rows` 调整至最多 2000000 行。每批仍需重新核验整条个人历史，且单场来源仍需完整载入；生产规模下的耗时尚未验证。也可在保护开启时显式设置 `ODOC_COMBAT_DAILY_BACKFILL=1`，由世界维护线程分批回填，默认关闭；批次时间限制只在两场之间检查，不保证单次核验在此时间内结束。所有设备的隔离与备份仍须按[归档方案](./todo/居民统计与战斗明细归档设计.md#回填前冻结旧归档与同步裁剪)执行。此阶段不核验完整资产及远端恢复条件，也不能清理明细。
- 后台默认启动后连续补齐已结束组队和旧单人战斗，每五分钟再检查新增场次；进行中活动不生成结算。迁移 `0103_combat_party_settlement`、`0106_combat_solo_settlement` 保存可同步的单场结果；手工每日回填仍可只生成版本 18 贡献。统计与七天清理由同一后台线程衔接，处理细节见[居民数据分析统计口径](./Agent居民数据分析统计口径.md#数据与同步)。
- 回填和自动贡献生成均持有业务与同步共用的本机互斥锁，并核验个人历史；每批结束后释放锁，但单场核验不受批次时间限制。大历史量下仍可能阻塞战斗推进及其他业务；真实生产负载和锁等待尚未测量。
- 旧版三方合并与发布按最大归档边界裁掉旧事实。本版在实际裁剪前检查本机、远端和基准快照：只要边界内仍有战斗事实，拒绝本次合并或发布，提示先分别备份、核对并回填；空边界可继续。旧设备仍可能执行旧裁剪，迁移期间须停止或隔离。旧归档同步协议为 16。
- 旧版个人归档可能使部分探索缺少真实出发事实，导致出发批次统计出现缺口。不能证明的历史不会被伪造；来源不完整时后台保留现有明细并暂停全部新清理。
- 组队来源校验按会话归集成员、波次和事件，并按共享事件及居民索引个人回执；个人探索校验按探索归集遭遇和事实，美食、炼金校验按探索归集出发事实，避免为每场探索重新扫描全量来源。仍逐项校验事实链、奖励归属、回执唯一性、遭遇序号、出发事实和终态，不改变同步协议或来源口径。
- 个人事实追加和回填核验时，状态指纹改为逐行读取、分批编码，产生与旧聚合 JSON 完全相同的 SHA-256，避免把整位居民的探索和遭遇历史同时保存在内存。隔离 PostgreSQL 中用 1250 次探索、24000 条遭遇的模拟数据，前后指纹一致，四次交错测量的耗时接近，Python 峰值内存由约 129 MB 降至约 4 MB；结果不代表真实生产吞吐。每个回合仍需遍历这些历史，尚未实现增量指纹，也不代表写入耗时随历史增长的问题已解决。

### 七天清理和恢复

自动线程处理完已结束组队和旧单人的待统计批次后，先检查所有账号的已结束来源是否都已覆盖。即便较新的战斗还未到七天，只要它未统计、缺少来源或校验失败，也暂停清理所有场次；进行中的战斗不进入积压。组队以最后一名成员的实际结束和离队时间为七天起点，旧单人以真实结束时间为起点。停机十四天、三十天或更久时先补齐全部积压，积压期间允许明细暂时超过七天。归档后的每日贡献缺失或损坏时，后台先核验保留的结算、链区间和个人状态，再重建派生统计；结算来源自身不完整时不猜测或覆盖。

符合条件的每批清理在业务写入和同步共用的本机互斥锁及同一事务内，先校验全量战斗来源、成长、装备和库存，再生成压缩结算、个人与共同链连续区间，验证删除后的数据仍可恢复，最后写入结算并删除对应 `round` 和本机修订行。探索快照内缓存的旧回合也会清除；出发、终态、遭遇、波次、奖励、经验、掉落及需要的资产依据保留。失败或中断会回滚整批，重复执行不会重复结算。清理后的旧场次不能回放攻击过程，但仍保留单场结果、图鉴发现和可按实际发生时间及出发批次重算的击杀。

压缩结算及链区间进入既有 WebDAV 快照，使用战斗同步版本 20；未删除的结算使用版本 19。旧完整快照与压缩结果合并前，会重新核对原始结算和链区间并去掉重复回合；无法证明一致时拒绝合并。用户主动完整恢复旧快照则恢复其原始数据，后台会重新统计和清理。旧远端快照与本机仍保持上次对齐时，单机同步可直接发布当前压缩快照。旧备份保留由现有备份策略决定，不等同于主库七天清理。

同一组队场次在不同设备各自清理时，数据库事件时间可能保留微秒，而通用快照序列化会截到毫秒。合并时先分别核验两份归档；若其余内容一致，逐事件时间只相差同一毫秒内被截掉的尾数，则保留较高精度的时间并重新计算归档摘要。两个不同的完整微秒时间或其他内容差异仍作为分叉拒绝。此兼容不改变快照格式或同步版本，不截断已有历史；参与同步的设备应更新代码。

后台核验使用共享互斥锁；大批历史的单场校验或清理事务可能阻塞其他业务，首次回填耗时、真实部署的接口速度与磁盘回收尚未测量。

清理前的全账号覆盖检查复用已核验的组队每日结果，并逐批读取结算载荷，避免同时把全部结算 JSON 留在内存；旧单人探索快照和组队每日贡献仍需全量检查。该优化不缩小阻断条件，生产规模耗时和锁等待仍需实际测量。

## 后台可见信息

「世界管理 → 冒险设置」展示当前规则版本、居民固化进度、历史/未结束冒险数量、同步目录数量，以及各目录的规则JSON字节数、运行引用和是否参与同步。字节数是规则JSON估算，不是数据库文件或压缩后的WebDAV传输体积。

目前没有编辑固化属性或手工删除事实的入口；旧目录仍只在本机保留且不随快照导出。旧归档命令仅支持只读预览；新后台只清理符合条件的个人和共同 `round` 以及探索快照中的回合缓存，保留出发、终态、遭遇、波次和结算等依据。

## 代码与验证入口

- `combat/history_snapshot.py`：旧快照核验、固化、聚合指纹和目录筛选；`combat/history.py`：事务内落库、运行引用和后台统计。
- `combat/equipment_snapshot.py`：独立装备穿戴条件；`combat/facts.py`、`combat/sync.py`：结果事实及协议8校验；路径相对 `system_settings/agent_world/`。
- `combat/test_history.py` 覆盖旧数据固化、不重生成装备、移除旧目录后穿戴/历史/同步、活动冒险保留旧规则、篡改拒绝、旧快照导入、重复恢复和账号隔离。所有恢复测试使用隔离数据库与临时媒体目录，未进行真实双设备WebDAV验收。
- `combat/retention_cleanup.py`、`retention_compaction.py`、`retention_sync.py` 和 `retention_merge.py` 实现七天清理和恢复核验；`test_retention_cleanup.py` 覆盖全局积压、七天边界、中断回滚、统计对照、旧快照合并及清理后的新战斗。
