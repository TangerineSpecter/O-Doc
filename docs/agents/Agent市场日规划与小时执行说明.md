# 市场日规划与小时执行说明

本文描述当前实现：市场从“每天一次机会”改为“每日规划 + 入库处置 + 每小时预检 + 命中进场”。新流程通过 `LifeConfig.settings.market_automation_v2` 开关灰度启用（默认关闭，验收后开启）；开关开启时不再生成新的每日 `market_prepare` 机会，关闭时仍走原每日机会路径。

## 一、每日市场规划

- 每位居民每天一份 `MarketPlan`，由每日生活规划后补齐；`ensure_plan` 生成，失败时保留已有处置策略、预算置 0、不新增采购目标。
- **代码算候选，决策模型选档位**：数量、价格上限、预算裁剪、可穿戴与属性过滤都在代码里完成，不再把库存、挂牌、商店快照整体交给付费文本模型，也不解析自由 JSON。每题候选不超过 10 个，单题状态约一千字符以内，每位居民每天最多 6 题。
- 提问顺序：种子（最多 2 题）→ 肥料（最多 2 题）→ 居民挂牌价格上限（1 题）→ 装备部位价格上限（1 题）。没有缺口或买不起的项直接跳过，不产生空题。
- 当天种植队列出现种子或肥料缺口时，`refresh_queue_needs` 按缺口金额直接生成采购目标，不提问、不调用模型；每日规划早于当天种植计划生成时，也能在当天小时内补上。缺口指纹写入 `context.needs_signature`，未变化不重复建目标；新增金额按可用余额上限补入预算，仍受生活资金预留约束。
- 数量档位由代码围绕缺口生成 `0 / 缺口一半 / 刚好补齐 / +1 / +2`，去重并剔除超出可用预算的档位；肥料题同时给出缺口、手头袋数、单价和效果（增产/品质）。
- 价格档位由代码按当前最低价生成 `不追 / 最低价 / +10% / +20%`，模型只选上限，不自己算金额。
- 决策链按世界设置“决策模型”里配置的顺序逐个尝试（`decision_connection_ids`，本机某连接成功后可在 TTL 内暂时沿用）；全部不可用时按“不新增采购”收官，**不回退到付费文本模型**。
- 答案按题目键写入 `MarketPlan.context.answers`；规划超时、进程重启或当天重试不会重复提问。`context.fallback` 记录降级原因，便于回看。
- 规划结果仍经 `validate_plan` 校验：预算不超过可用预算，商店目标只能选当小时商店或常驻农资，挂牌目标只能选可交易 sku，装备目标按部位且数量固定 1。
- 装备目标每天重算；当前装备、等级、职业、背包装备签名未变时沿用昨日未完成装备目标，并把沿用金额计入当日预算，剩余预算不足则跳过。挂牌求购目标按聚合到的最高星设置 `min_stars`，避免用高星价格买低星商品。

代码入口：`market_planning.py`（逐题提问与组装）、`market_plan_candidates.py`（档位计算、报价与装备过滤）、`system_settings/management/commands/plan_market_day.py`。

## 二、入库处置标记

- 美食、炼金成品、农作物、畜产品、炼金材料、纪念品入库后进入 `MarketDispositionTask` 队列（来源：烹饪、炼金、收获、迷宫掉落、购买、撤单返还、历史补标记）。
- 独立 worker 按 sku 逐题询问决策模型：目标持有量 → 处置渠道 → 出售/上架比例 → 星级顺序 → 挂牌价倍数。问题拆开问，不合并数量与星级候选。
- 答案为按 sku 长期有效的 `MarketDisposition`：`target_hold`、`sell_ratio`、`list_ratio`、`star_order`、`list_price_ratio`。新产出自动套用，不重复问模型。
- 模型不可用时按“保留当前可用库存 + 待复核（`status=review`）”落库，下次日规划重新入队；不允许永久自用或全部卖掉。
- 每个任务保存问题答案缓存；每轮最多 20 个问题、60 秒，超出顺延。`running` 超过 5 分钟未更新时由调度入口及 worker 恢复为待处理，保留已有答案继续；条件更新认领防止同一任务被并发消费。
- 历史库存用 `python manage.py backfill_market_dispositions` 入队，加 `--run` 同时消费队列。

代码入口：`market_disposition.py`、`market_disposition_worker.py`、`management/commands/backfill_market_dispositions.py`。

## 三、可交易品类与出售路由

- 可挂牌：农作物、畜产品、美食、炼金成品（`elixir.`）、炼金材料（`combat.material.`）、纪念品。
- 商店回收：农作物、畜产品、美食走 `sell`；炼金材料走 `sell_combat_material`；炼金成品与纪念品不能商店回收，只能挂牌。
- 种子、肥料、饲料仍不可回收、不可挂牌。
- 挂牌数量立即转入托管；撤单返还和买入都会重新进入处置队列。
- 执行时按炼金计划软预留重新计算可处置量；探索携带在出发准备时按当时库存重新选择，处置策略的 `target_hold` 负责日常保留。星级顺序由执行器显式按星选行，不依赖 `split_item` 的行内 FIFO。

## 四、小时预检与进场

- 每小时为每位活跃居民生成唯一 `MarketTick`，执行分钟为“居民 + 小时”稳定随机，范围 1–54，避开整点与每小时最后 5 分钟。
- 预检只读：待处置超量、目标匹配的商店批次/挂牌、到期改价、装备候选；不建会话、不扣体力、不占世界执行位。唯一写入是补入当天种植队列缺口对应的采购目标（见第一节），补目标失败只记日志，不跳过本轮其他动作。
- 没有动作记 `skipped`；有动作才进场，扣 5 体力，开 5 分钟会话。
- 装备目标命中后逐件判断：代码先剔除永久不买、按穿戴规则不可穿戴（职业/等级/部位，戒指按 `ring_1`/`ring_2` 区分）以及属性无任何提升的候选，再让决策模型选择“买下 / 不买这件”。不买写入 `MarketNoBuy`（按 `equipment_id` 永久），实例卖给商店、实例删除或居民归档时清理。
- 同一居民一小时最多一次进场；错过整点不补跑。
- 批量处置与采购走 `market_batch.execute`，直接调用 `market_service.trade`，不经过 20 次工具调用计数；每笔使用稳定请求键，单笔失败只记录原因。顺序为：撤回/改价 → 出售/上架 → 采购。出售和上架共享星级顺序，上架选行跳过本轮已分给出售的数量，避免重复分配同一批库存；常驻肥料不受有限商品库存字段限制。

代码入口：`market_tick.py`、`market_batch.py`、`market_no_buy.py`、`action_runner.tick`。

## 五、预算与收入

- 当日预算挂在 `MarketPlan`，多次进场共用；每笔采购在同一资产事务内锁定居民、计划和未结束生活安排，按 `min(budget - spent, 真实余额 - 最新生活预留)` 校验。以实际成交金额累计支出，成交、目标进度和计划记账一起提交，失败全部回滚；同一交易键重放不重复计入进度或支出。
- 挂牌不是收入，只有成交才记账；上架预期收入不能计入当日预算。
- 处置执行时按当前炼金软预留重新计算可处置量，避免把已排炼金要用的材料挂走；探索用药水由 `target_hold` 保留，出发准备仍按当时库存决定携带。

## 六、数据与同步

同步资产（纳入 WebDAV 与市场完整性检查点）：`MarketPlan`、`MarketGoal`、`MarketDisposition`、`MarketNoBuy`。
`MarketPlan.context` 里的题目答案与降级原因随计划同步，另一台设备恢复后不会重复提问。
不同步的本机执行状态：`MarketTick`、`MarketDispositionTask`（队列与预检进度可重建，避免另一台设备重复执行）。两者列入 `system_settings.sync_state.LOCAL_ONLY_MODEL_LABELS`，不导出，也不记录同步修订。

旧检查点只包含六项核心资产；`normalize_legacy_dates` 会识别旧哈希并一次性重建，不接受缺失或篡改的资产。

## 七、当前边界

- 自动降价只做“超过两天挂牌每天最多下调 10%，且不低于回收价”，不自动撤回；后续可补滞销回收规则。
- 手动 MCP（对话中显式绑定世界市场 MCP）不受处置标记约束，保持原工具语义。
- 每日规划、处置标记与装备判断都走“结构化决策”连接链（`jev_enabled` 开启且场景未被排除）。未启用或连接全部失败时：日规划按“不新增采购”降级，处置按“保留 + 待复核”降级，装备不买不会写入；三者都不回退付费文本模型。
- 市场页“市场规划”标签展示当日预算、目标、处置策略、不买清单和小时预检原因。

## 八、改造记录（2026-10-20）

**背景**：早期市场决策把 MCP 查询结果（几十上百条物品、价格、来源、历史）整包交给大模型，单次输入暴增。后续虽然给日规划做了上限，仍是“一位居民一天一次整包 JSON”，典型约 4.4k 字符、打满上限约 1.2 万字符；格式失败还会触发 `repair` 整包重发，并按“决策模型 → 居民模型 → 系统默认模型”逐个兜底，费用进一步放大。

**现状**：
- 日规划改为“代码算候选 + 决策模型选档位”，每位居民每天最多 6 题，每题最多 10 个候选、状态约一千字符，单次规划不再调用付费文本模型。
- 数量档位由 `market_plan_candidates.quantity_options` 围绕缺口生成（0 / 一半 / 缺口 / +1 / +2，去重且过滤买不起的档位）；价格档位为 0 / 最低价 / +10% / +20%。
- 决策链按世界设置中“决策模型”的顺序尝试；答案写入 `MarketPlan.context.answers`，超时或重启后按题复用，`context.fallback` 记录降级原因。
- 决策全部不可用时按“不新增采购”收官，避免在模型异常时自动花钱。

**可调参数**：
- 题量：`market_planning.SEED_QUESTIONS` / `FERTILIZER_QUESTIONS` / `LISTING_QUESTIONS` / `EQUIPMENT_QUESTIONS`，总上限 `market_plan_candidates.MAX_QUESTIONS`。
- 档位：`quantity_options` 的 `±1/±2` 粒度、`price_options` 的 10%/20% 步长与 `MAX_OPTIONS`。
- 观察入口：`MarketPlan.context.answers`（实际选择）、`context.fallback`（降级原因）、`market_plan` 场景的 token 用量记录、`plan_market_day` 命令输出。

**评审修正（同日）**：沿用昨日装备目标时把金额计入当日预算、预算不足则跳过；挂牌目标按聚合最高星设置 `min_stars`；逐题预算扣除已承诺金额；装备签名按 `pk` 排序避免漂移；`validate_plan` 增加目标总额不超过预算的校验；降级文案改为“未完成的项不新增采购”。

**后续若调整**：先改本文件与 `Agent市场决策执行说明.md`，再动 `market_plan_candidates.py` 的档位或 `market_planning.py` 的题量，保持“代码算数、模型只选档位”的边界。
