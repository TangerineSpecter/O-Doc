# 市场日规划与小时执行说明

本文描述当前实现：市场从“每天一次机会”改为“每日规划 + 入库处置 + 每小时预检 + 命中进场”。新流程通过 `LifeConfig.settings.market_automation_v2` 开关灰度启用（默认关闭）；开关入口在「设置 → Agent → 任务 → 市场交易 → 配置 → 市场自动化」，保存市场任务时由 `AgentTask.market_config.market_automation_v2` 同步写入该账号的 `LifeConfig.settings`。这是即时运行开关，执行直接读取当前生活配置，不受 `LifeCycle.snapshot` 冻结影响。开启后不再生成新的每日 `market_prepare` 机会；尚未执行的旧版每日机会在开启状态下到点会取消。关闭后恢复原每日机会路径；已排队但尚未执行的小时预检会跳过，已启动的市场会话继续完成。

开启前需确认：本机世界自动执行已开启、当日市场计划可由每日生活规划生成、世界设置中的结构化决策连接可用（不可用时按“不新增采购 / 保留待复核”降级，不回退付费文本模型）。

## 一、每日市场规划

- 每位居民每天一份 `MarketPlan`，由每日生活规划后补齐；`ensure_plan` 生成，失败时保留已有处置策略、预算置 0、不新增采购目标。
- **代码算候选，决策模型选档位**：数量、星级、价格上限、预算裁剪、商品用途与报价过滤都在代码里完成；装备可穿戴检查独立按小时执行，属性优劣由居民逐件判断，不把库存、挂牌、商店快照整体交给付费文本模型，也不解析自由 JSON。每题候选不超过 10 个；每位居民每日规划最多 8 次有限提问，覆盖完整已有需求序列。缓存命中和唯一合法选项由代码处理，不消耗模型问题额度。
- 提问顺序：种子（最多 2 题）→ 肥料（最多 2 题）→ 鱼饵数量区间（最多 1 题）→ 该区间准确份数（最多 1 题）→ 一种居民挂牌商品的最低需求星级（最多 1 题）→ 该星级的求购价格上限（最多 1 题）→ 装备部位价格上限（最多 1 题）。没有缺口、没有合法报价或买不起的项直接跳过，不产生空题。
- 居民挂牌中的食材与炼金材料先做代码用途过滤：按居民当前等级、食谱/炼金规则和扣除其他开放制作计划预留后的背包库存，模拟增加 1 件该 SKU；只有至少一种配方的可制作份数因此增加，才进入决策候选。体力属于可恢复资源，不作为用途过滤条件；执行成交前会再次核验，避免计划生成后材料状态变化造成无效采购。成品、纪念品等非制作原料仍走原有挂牌判断。
- 当天种植队列出现种子或肥料缺口时，`refresh_queue_needs` 按缺口金额直接生成采购目标，不提问、不调用模型；每日规划早于当天种植计划生成时，也能在当天小时内补上。缺口指纹写入 `context.needs_signature`，未变化不重复建目标；新增金额按可用余额上限补入预算，仍受生活资金预留约束。
- 种子与肥料的数量档位由代码围绕缺口生成 `0 / 缺口一半 / 刚好补齐 / +1 / +2`，去重并剔除超出可用预算的档位；肥料题同时给出缺口、手头袋数、单价和效果（增产/品质）。鱼饵单独按 `0～9 / 10～19 / … / 90～99` 分区间，先按该种库存最多 99 份与预算裁剪末区间，再只展开所选区间的最多十个整数；0 表示不买。持有 15 份时末区间会裁为 `80～84`，但可用鱼饵已有 15 份本身不会触发自动补购。鱼饵参考缺口 12 份只决定是否触发补购，不限制所选数量。
- 挂牌商品先按 SKU 与真实星级聚合报价，排除无货、自有挂牌、其他账号和非法星级；每种商品最多五个星级档位。每档表示最低需求星级，附满足该门槛的真实数量和最低报价，仅保留至少买得起一件的档位。先选择最低需求星级，不将星级、数量和价格相乘。
- 星级确认后只重新查询同 SKU 且不低于所选星级的真实挂牌，再提供 `不追 / 该星级最低价 / +10% / +20%`，并去掉超过本次剩余预算的价格；数量固定一件，金额由代码计算。一星 10 元、五星 100 元时，选择至少五星就从真实 100 元定价，不能拿一星的 10 元搭配五星需求。选星后库存消失或报价已买不起时跳过本项，不自动降星。装备不在日规划阶段定部位、定价格上限，改为小时进场后逐件判断。
- 决策链按世界设置“决策模型”里配置的顺序逐个尝试（`decision_connection_ids`，本机某连接成功后可在 TTL 内暂时沿用）；全部不可用时按“不新增采购”收官，**不回退到付费文本模型**。
- 答案按题目键写入 `MarketPlan.context.answers`；鱼饵区间使用 `bait-range:{sku}`，准确份数使用 `bait-quantity:{sku}:{range}`；最低需求星级使用 `listing-stars:{sku}`，价格使用 `listing:{sku}:stars:{min_stars}`。恢复已有规划时沿用仍合法的答案；已确认星级没有候选时跳过，不因候选减少而重抽或降低要求。旧版单题鱼饵答案和不带星级的价格答案不会用于新分阶段问题。`context.fallback` 记录降级原因，便于回看；没有新增表、字段或同步实体，答案沿用已同步的计划 JSON。已生效旧计划保持原状，不批量重算。
- 规划结果仍经 `validate_plan` 校验：预算不超过可用预算，商店目标只能选当小时商店或常驻农资，挂牌目标只能选可交易 sku，旧记录中的装备目标按部位且数量固定1校验，新日规划不再生成这类目标。
- 不再生成或沿用每日装备部位目标；已经保存的开放旧装备目标在下一次小时预检中标为取消并释放其未花预算，保留记录且不重复释放；不再以它们限定购买部位或价格。挂牌商品目标的 `min_stars` 来自已确认的最低需求星级，价格与数量依据同一门槛下的真实报价；实际成交继续复核星级、版本、用途、余额与生活资金预留。

代码入口：`market_planning.py`（逐题提问与组装）、`market_plan_candidates.py`（档位计算、报价与装备过滤）、`system_settings/management/commands/plan_market_day.py`。

## 二、按用途保留目标与每日复核（2026-11-06）

- 可处置库存包含作物、畜产品、美食、炼金成品、战斗材料和纪念品。物品仍按稳定 SKU 和星级保存在共用背包，不给具体物品增加长期用途标记。
- 每个 SKU 的新版策略保存于 `MarketDisposition.strategy`：`version=1`、`targets`（炼金 `alchemy`、烹饪 `cooking` 或成品/纪念品 `self_use`）、`retain_order` 和 `reviewed_date`。已有渠道、比例、处置顺序和价格字段继续使用；`target_hold` 只作历史兼容与目标合计展示，不再决定新版交易。
- 每日按居民、上海日期、SKU 复核有库存或有效需求的物品。已有新版策略先问沿用/调整；首次及旧策略直接制定。每个用途独立问目标个数，再问保留顺序、超量渠道、分配比例、处置顺序和挂牌价。当前无超量也制定完整未来规则；不再按少于三件默认永久自用，也不以当前库存一半/全部生成目标。
- 原料候选按该 SKU 配方最大单份用量的 0/1/3/5/10 倍生成，并加入合法新版旧目标；成品为0/1/3/5/10/20，纪念品为0/1，加旧目标。没有对应配方的原料备用目标只能为0。输入包含配方等级门槛、已有成品、近七日实际消耗和市场需求统计。单题最多十项，唯一选项由系统确认，无普通文本模型兜底。
- 答案、输入规则指纹和复核状态保存在当日 `MarketPlan.context.inventory_policy_reviews`，逐 SKU 完整确认后原子发布；同日入库只套用完整策略。规则或策略修订变化使缓存失效。连接不可用保留最近完整新版策略，首次或旧策略暂无新版时保守保留。每个本机任务最多三次异常/连接尝试，问题额度或时间用完顺延；轮询使用既有每次5题/20秒预算，手动 worker 默认20题/60秒。
- 复核初始化、逐题答案、失败待复核状态和完整策略发布均在共享 `farm_gate` 与短事务中写入；先取业务锁再取计划行锁，与资产交易、快照导出和恢复互斥，避免市场检查点混用不同时间的资产。每日采购答案沿用相同锁顺序；模型请求在业务锁外执行。
- 世界轮询的兜底全量扫描在每个本机进程内按居民最多每5分钟一次，上海日期变化和本机缓存清空后可立即补扫；扫描失败下轮重试。每日规划成功仍直接扫描，新产物仍直接入队；新增有效需求通过下一次兜底扫描补齐，不用“今天已有任意任务”判断扫描完整性。恢复后最迟下一次兜底扫描补齐本机任务，任务按居民/日期/SKU去重。
- 自动复核要求本机世界执行开启、账号市场自动化开启、居民参与且未暂停；恢复数据不授予运行许可。本机队列按居民、日期、SKU 去重。超过五分钟的 running 恢复；旧日期任务结束，由今日重建。新设备可用同步的市场计划答案接续，但不能通过恢复获得执行许可。旧策略在完成新版复核前不自动处置；升级不直接出售或重写历史交易。
- 统一保护计算：同用途保护 `max(备用目标, 未执行承诺)`，不同用途相加。已冻结批次先分配，之后为其他制作/探索需求、剩余锻造目标、备用目标。同一件锻造目标和其提交中冻结材料只计算一次，已完成制作从需求中扣除。库存不足时全部保留、显示缺口，可处置为0。
- 保留顺序与处置顺序分别决策。烹饪计划沿用自己已确认的用料星级；备用目标才使用保留顺序。无星级的战斗材料使用稳定 FIFO，不提星级问题。锻造需求随有效目标、规则、完成和失效实时变化。
- 备用量只约束自动出售/挂牌，不阻止对应活动消费，不生成采购订单。托管挂牌不计入可用背包，也不因新目标自动撤单。
- 鱼不进入策略队列：正常市场进场按批次自动回收普通鱼，鱼王和托管挂牌保留；鱼不单独构成进场理由，战斗补给商店和探索准备不触发回收。

代码入口：`inventory_policy.py`（版本和候选）、`inventory_protection.py`（统一分配）、`market_policy_facts.py`（只读模型投影）、`market_policy_review.py`（逐题进度）、`market_review_schedule.py`（本机补扫限频）、`market_expiry_index.py`（检查点驱动的期限投影）、`market_disposition_worker.py`（本机认领与额度）。

## 三、可交易品类与出售路由

- 可挂牌：农作物、畜产品、美食、炼金成品（`elixir.`）、炼金材料（`combat.material.`）、纪念品。
- 商店回收：农作物、畜产品、美食走 `sell`；炼金材料走 `sell_combat_material`；炼金成品与纪念品不能商店回收，只能挂牌。
- 鱼：进入市场会话即由代码按批次回收价自动全部出售（鱼王和托管挂牌除外），不参与处置策略或挂牌候选。
- 种子、肥料、饲料仍不可回收、不可挂牌。
- 挂牌数量立即转入托管；撤单返还和买入都会重新进入处置队列。到期返还也入队，但依据已有到期撤单交易识别该批库存，自动挂牌不会直接重新上架；新产出不并入该退回批次，手动会话仍可明确选择上架。
- 预检、批次选择和逐笔成交前均用统一保护计算；事务内核验策略修订和该行可处置数量，变化则跳过等待重查。出售和挂牌比例合计100%，挂牌取得出售计算后的余数，避免零散尾数。材料出售取消99件限制，复用市场1～1000000正整数校验且不超过实时可用量；药剂购买仍最多20瓶，装备仍单件。
- 铁匠铺活跃目标按实时配方保护已有材料，即使尚未凑齐也不会出售；完成、取消或失效立即释放。没有可出售量仍可制定未来策略。手动 MCP 继续沿用明确操作语义与既有业务校验。

## 四、小时预检与进场

- 每小时为每位活跃居民生成唯一 `MarketTick`，执行分钟为“居民 + 小时”稳定随机，范围 1–54，避开整点与每小时最后 5 分钟。
- 预检先检查：待处置超量、目标匹配的商店批次/挂牌、到期改价，以及本人可穿戴且尚未明确拒买的他人装备挂牌；不建会话、不扣体力、不占世界执行位。预检可以补入当天种植队列缺口对应的采购目标（见第一节），并执行小时鱼饵补购决策；两者失败各自记日志，不跳过本轮其他动作。
- 挂牌期限由已有上架时间和降价历史推导，在本机内存中按现有市场挂牌检查点缓存；挂牌变更或恢复后检查点变化即重建，翻页复用期限、数据库计算精确总数和分页，不设可访问数量上限。交易提交继续核验实时挂牌。到期维护默认每轮最多成功50条、尝试200条；同版本同期限返还失败退避10分钟并保留诊断，版本/期限改变可立即重查，失败批次不挡住后续挂牌。缓存只用于派生读取和调度，不参与同步或授予执行权限。
- 已启用新版自动经营时，首次上架或最近改价满一天后才可能生成自动降价，每次最多约10%，不低于参考价值。每次成功降价让挂牌再有效48小时；没有降价、提价或同价均不延长。到期维护独立运行并优先于小时预检，失效报价不作为采购和装备候选。
- 鱼饵小时补购：开启钓鱼、可用库存少于12份且本小时有适用报价时，若同种没有未完成目标，额外最多问两题（数量区间→准确份数），不占每日八题。候选扣除生活预留与全部未完成采购承诺，并受单种99份上限约束；无报价、库存充足或买不起直接跳过。有效答案按 `hourly-bait:<批次ID>:<sku>` 保存在既有 `MarketPlan.context.answers`，同批不重复询问，不买也复用，下一小时重新评估。连接失败保留已答步骤、不新增采购，不回退文本模型；提交前在资产锁和事务中复核最新需求与资金，只缩减不放大选择，稳定目标ID避免重复建单，按必要金额补足当日预算。
- 没有动作记 `skipped`；有动作才进场，扣 5 体力，开 5 分钟会话。
- **小时进场判断（2026-10-26）**：不要求空槽或每日装备采购目标，不检查属性是否提升，也不按价格提前隐藏可穿戴候选。剔除本人、其他账号、失效挂牌、不可穿戴及已有 `MarketNoBuy` 的实例；戒指按两个合法戒指位检查，但每个实例只计数一次。不先截取全市场前若干件再过滤，避免已拒买的旧挂牌挡住新候选。
- 已确认的采购、库存处置、改价、撤回或装备处置意向有可执行动作时，不再询问去不去市场，直接尝试进场；无动作时跳过。仅有未判断装备候选、没有上述计划动作时，仍向 `market` 场景提供装备类型/数量、可用资金及进场体力，由居民选择是否前往；不去或连接不可用不标记装备。实际入场继续检查居民忙碌、体力与承诺保护，成功才扣5点体力。
- 进场遇到探索、钓鱼、旅行或其他居民占用时，保留一个本机待执行的小时机会，约每分钟重查；自由活动在此机会处理前不新开工。居民占用先于体力检查判定，避免忙碌且体力暂不足时丢掉等待机会；空闲后仍重新检查体力和资源保护。跨小时只保留同一机会，重查时使用当时真实报价与目标，机会已消失则结束；同日完成后跳过同小时重复机会。跨日、暂停或关闭自动执行时不补跑旧机会。执行中异常和资源不足不重复成交；已成交事实仍按稳定请求键保护。
- **装备暂选与统一购买（2026-10-27）**：进场后恢复 `MarketPlan.context.equipment_selection` 版本1。以身上装备为初始基准，先逐件比较尚未处理的自有可穿戴装备（含已买未穿），再比较他人挂牌；自有在售装备不作为可用基准。持有装备、穿戴、职业、等级或暂选报价变化时重建比较。没有变化时复用已确认基准，不反复比较同一批背包。
- 普通部位每题只输入职业、等级、对应暂选完整属性与价格、一件候选完整属性与价格、是否已拥有、可用资金及暂选总预留；选择“替换暂选 / 保留暂选”。选中只是暂选，暂不成交；明确不选或被替换的市场实例写入 `MarketNoBuy`，按居民与 `equipment_id` 永久生效，不因降价重问。自有装备不写拒买、不出售。
- 戒指每枚单独决策“替换戒指位1 / 替换戒指位2 / 保留两位”，同时展示两位暂选；新戒指只占一位，被替换的市场戒指永久拒买，最终最多买两枚不同实例。
- 主副手先分别比较单手武器、副手、双手武器。全量比较结束后，存在双手竞争且有多个不同方案时，独立询问“单手＋副手 / 双手 / 原有主副手”，附完整属性、各组合总价、其他部位采购总额及可用资金，等价方案去重。没有双手竞争或仅一个方案时由系统采用。选择双手时不带副手，本轮未留下的市场主副手永久拒买；已拥有的装备保留。
- 替换前核验完整暂选预留不超资金；主副手两条互斥方案只预留较大总价，戒指和其他部位累计预留，避免单件都买得起、整组超预算。报价或持有装备中途变化、连接故障、会话停止、资金不足及成交失败不新增拒买标记；此前已确认的拒买仍保留。
- 每场装备比较与组合选择共最多20次模型决策，受5分钟会话限制；达到上限或中断时保存阶段、暂选和剩余候选，跨小时、跨日续比，不提前购买。小时预检仍在模型调用前条件认领。
- 比较完成后，在资产互斥与同一数据库事务内重新读取全市场合法候选；出现新候选先加入剩余比较。复核报价、归属、可穿戴条件、整组总价、生活预留及日预算后，只购买最终暂选；任一成交失败则整组回滚，保留方案下次复核。请求键绑定比较批次，不绑定小时，防止重试重复记账。成功后不自动换装，已买未穿装备留作后续基准。实例真正消失或居民归档时沿原规则清理拒买。
- 同一居民一小时最多一次进场；普通错过的小时不补跑，因忙碌保留的机会可在当天跨小时执行一次。
- 批量处置与采购走 `market_batch.execute`，直接调用 `market_service.trade`，不经过 20 次工具调用计数；每笔使用稳定请求键，单笔失败只记录原因。顺序为：撤回/改价 → 库存出售/上架 → 已确认装备处置意向 → 采购。装备意向不重新询问用途；出售直接执行，挂牌价格从既有五档有限选择。已选价格按意向事实ID保存在同步的市场计划答案中；失败或恢复后沿用。仅有待挂牌且缺少定价场景/连接时不进场，不白扣体力。出售和上架共享星级顺序，上架选行跳过本轮已分给出售的数量，避免重复分配同一批库存；常驻肥料不受有限商品库存字段限制。

代码入口：`market_tick.py`、`market_bait_refresh.py`、`market_batch.py`、`market_equipment_candidates.py`、`market_equipment_shopping.py`、`market_equipment_selection.py`、`market_equipment_progress.py`、`market_equipment_settlement.py`、`market_no_buy.py`、`world_cycle.tick`。

## 五、预算与收入

- 当日预算挂在 `MarketPlan`，多次进场共用；按日目标采购在同一资产事务内锁定居民、计划和未结束生活安排，按 `min(budget - spent, 真实余额 - 最新生活预留)` 校验。以实际成交金额累计支出，成交、目标进度和计划记账一起提交，失败全部回滚；同一交易键重放不重复计入进度或支出。
- 小时装备购买独立于日采购目标，逐笔使用“真实余额 − 最新生活预留 − 日计划未花预算”的剩余资金；日计划采购先执行，已花部分不再占预留。装备成交时在同一事务给 `budget` 和 `spent` 同额增加实际成交金额，保留其他日采购额度；无可用资金或实际报价超限则失败，不写拒买。重放已成功的交易不重复增加金额。
- 挂牌不是收入，只有成交才记账；上架预期收入不能计入当日预算。
- 处置执行按各用途目标、制作承诺、探索预约和锻造目标统一保护；出发准备与制作继续复核当时真实库存。

## 六、数据与同步

同步资产（纳入 WebDAV 与市场完整性检查点）：`MarketPlan`、`MarketGoal`、`MarketDisposition`、`MarketNoBuy`。
`MarketDisposition.strategy`、`MarketPlan.context.inventory_policy_reviews` 随业务资产同步；策略声明 `market_strategy_schema_version=1`，无新版策略且无新版复核进度时为0。迁移0107先核验原市场检查点，再加入空策略字段并显式重算指纹；旧快照只在严格匹配未带空字段的旧哈希时转换，不重建冲突资产。策略和复核格式在来源、合并、导入和恢复中验证。所有自动执行设备须升级和迁移后交换新版数据。

`MarketPlan.context` 里的题目答案、降级原因及 `equipment_selection` 版本1随计划同步。装备进度包含批次ID、持有装备指纹、原有配置、各部位暂选、剩余逐件候选、已纳入比较的实例、组合阶段和最终方案；纳入既有市场完整性哈希，恢复验证格式、版本、实例不重复及双手互斥。旧计划缺少该键时按新批次开始，无数据库迁移。
恢复仅保留业务选择，不启动模型、不恢复旧会话许可；下一次本机正常授权进场时重新核验真实装备、报价和资金。跨日读取最近市场计划中的比较状态并写入当天计划；历史计划保留当时进度。所有参与自动执行的设备须升级到支持该规则的代码，避免旧设备仍按逐件即时购买执行。
不同步的本机执行状态：`MarketTick`、`MarketDispositionTask`（队列与预检进度可重建，避免另一台设备重复执行）。两者列入 `system_settings.sync_state.LOCAL_ONLY_MODEL_LABELS`，不导出，也不记录同步修订。

旧检查点只包含六项核心资产；`normalize_legacy_dates` 会识别旧哈希并一次性重建，不接受缺失或篡改的资产。

## 七、当前边界

- 自动降价只做“超过两天挂牌每天最多下调 10%，且不低于回收价”，不自动撤回；后续可补滞销回收规则。
- 手动 MCP（对话中显式绑定世界市场 MCP）不受处置标记约束，保持原工具语义。
- 每日规划、处置标记与装备判断都走“结构化决策”连接链（`jev_enabled` 开启且场景未被排除）。未启用或连接全部失败时：日规划按“不新增采购”降级，处置沿用最近完整新版策略；无完整新版时保留库存待复核，仅装备候选的进场判断不可用则不进场，暂选比较或组合判断不可用时保存进度，不写新的不买标记；均不回退付费文本模型。已有计划动作不依赖进场判断连接。
- 市场页“市场规划”标签展示当日预算、目标、用途目标、承诺、实际保护、缺口、可处置量、复核状态、不买清单和小时预检原因；部分失败以红色状态及展开明细展示。
- 市场动态与每日活动的批量操作明细共用 `MarketTick.hits.outcome.done` 中的实际完成顺序；同一调度时间不按交易哈希 ID 推断先后。旧记录或同步到另一设备后缺少本机预检记录时，交易按时间与 ID 稳定回退；每日活动中的批量会话始终先显示进场、最后显示离场，包括历史上装备逐件交易时间晚于离场记录的情况。新批量会话在实际处理结束时记录离场时间。

## 八、历史改造记录（2026-10-20，装备日目标已于2026-10-26改为上述小时流程）

本节保留当时的实施记录。其中“每日最多六题”和“聚合最高星作为需求”已由第一节的 2026-10-23 当前规则替代：日规划最多八题，装备由2026-10-26小时流程接管；商品先确认最低星级，再用同一门槛的真实报价定价。

**背景**：早期市场决策把 MCP 查询结果（几十上百条物品、价格、来源、历史）整包交给大模型，单次输入暴增。后续虽然给日规划做了上限，仍是“一位居民一天一次整包 JSON”，典型约 4.4k 字符、打满上限约 1.2 万字符；格式失败还会触发 `repair` 整包重发，并按“决策模型 → 居民模型 → 系统默认模型”逐个兜底，费用进一步放大。

**现状**：
- 日规划改为“代码算候选 + 决策模型选档位”，每位居民每天最多 9 题，每题最多 10 个候选，单次规划不再调用付费文本模型。
- 种子和肥料由 `market_plan_candidates.quantity_options` 围绕缺口生成（0 / 一半 / 缺口 / +1 / +2，去重且过滤买不起的档位）；鱼饵分区间与准确份数两题；价格档位为 0 / 最低价 / +10% / +20%。
- 决策链按世界设置中“决策模型”的顺序尝试；答案写入 `MarketPlan.context.answers`，超时或重启后按题复用，`context.fallback` 记录降级原因。
- 决策全部不可用时按“不新增采购”收官，避免在模型异常时自动花钱。

**可调参数**：
- 题量：`market_planning.SEED_QUESTIONS` / `FERTILIZER_QUESTIONS` / `LISTING_QUESTIONS` / `EQUIPMENT_QUESTIONS`，总上限 `market_plan_candidates.MAX_QUESTIONS`。
- 档位：种子/肥料 `quantity_options` 的 `±1/±2` 粒度、鱼饵十位区间与区间内逐份候选、`price_options` 的 10%/20% 步长与 `MAX_OPTIONS`。
- 观察入口：`MarketPlan.context.answers`（实际选择）、`context.fallback`（降级原因）、`market_plan` 场景的 token 用量记录、`plan_market_day` 命令输出。

**评审修正（同日）**：沿用昨日装备目标时把金额计入当日预算、预算不足则跳过；挂牌目标按聚合最高星设置 `min_stars`；逐题预算扣除已承诺金额；装备签名按 `pk` 排序避免漂移；`validate_plan` 增加目标总额不超过预算的校验；降级文案改为“未完成的项不新增采购”。

挂牌商品改为最低需求星级与价格上限分题，已确认星级不因报价失败或候选减少而降低。当时隔离测试覆盖一星十元／五星一百元的真实查询、剩余预算过滤、唯一星级与缓存、报价中途变化、库存消失、无候选、无普通模型回退，以及当时全部需求八题可执行；商品星价、市场自动化和制作用途回归共 51 项通过。该段是分阶段验收记录；当前题量见第一节。模拟测试不替代真实决策连接质量、实际 usage 或双设备 WebDAV 验收。

## 2026-11-06 本地验收与升级
