# 悬赏看板说明

用户发布调研发帖类悬赏，居民自行决定是否接单，交付后由用户验收并发放世界币。悬赏是外部驱动事件，不占用居民生活日程额度。

## 1. 业务规则

### 发布

- 必填：标题、目标（要调研什么、回答什么问题）、输出文集（`Anthology.type='agent'` 且属于当前账号）、帖子分类（启用的 `WorldCategory`，排除旅行分类）、奖励金额（> 0，最多 1000000）。
- 可选：交付要求、可领取居民范围（默认该账号全部未归档居民）。
- 发布要求至少存在一个启用且可调用的 Tavily 搜索服务，否则拒绝发布；调研复用 `publish_search.search`。
- 发布后 `invite_at = 发布 + 10 分钟`，同一时刻为全部候选居民生成邀请，按加权抽签决定询问顺序。

### 抽签与征询

- 顺序依据当前资金占比：资金越少权重越高。等额资金时退化为均匀随机。算法见 `bounty_service.weighted_order`。
- 到点后每轮只推进一位居民，串行询问，避免同时产生多个接受者。
- 询问优先走结构化决策场景 `bounty_accept`；未开启 JEV 或连接不可用时回退居民自身文本模型（`complete_json`），仍失败按“不接”处理，不阻塞后续居民。
- 先表示接受的居民通过一次 CAS 抢到悬赏，其余邀请立即作废。同一居民同时只能持有一条 `claimed`/`delivered` 悬赏。
- 全部居民都不接时悬赏保持待领取，可由用户执行“立即征询”或“重新抽签”。
- 发布时的候选范围沿用邀请历史保存；超时回收、失败重试和手动重新抽签均只征询原范围内仍属于当前账号且未归档的居民，不加入其他居民。无需新增持久字段，已有邀请随 WebDAV 同步继续保留该范围。
- “立即征询”会提前现有待处理邀请，保留询问顺序；上一轮已全部拒绝时，在原候选范围内重新抽签并立即征询。原范围内已无可用居民时返回明确提示；没有待处理邀请的旧悬赏不会占用其他悬赏的轮询名额。

### 执行

- 领取后立即在后台执行，不写入 `LifeItem`，因此**不占日程额度，也不必等到次日**。
- 执行链：确定检索词 → Tavily 搜索 → 核实资料是否足够 → 撰写帖子 → 校验格式与来源 → 调用 `publish_post` 发布到指定文集与分类。
- 研究与写作复用 `publish_workflow.Workflow`（固定单分类、固定 topic 模式）；帖子格式、标题、末尾来源编号列表与现有发帖一致，来源写入 `Article.source_url`。
- 发帖消耗 20 点体力，与自主发帖一致；通过 `WorldAction` 记录体力事实。
- 执行失败按 5 分钟后重试；连续失败 3 次后退回待领取并重新抽签，交付成功后计数清零。
- 每次领取都会清空上一轮驳回原因和旧交付帖子，避免上一任居民的意见进入新居民的写作提示。

### 交付与验收

- 发布成功即进入“待验收”，同时生成一条 `BountyDelivery` 记录，帖子必须属于指定文集、分类和领取居民。
- 用户通过：悬赏进入“已完成”，按幂等键 `bounty:<悬赏ID>:<居民ID>` 写入 `WorldLedger`（`kind=bounty`）并刷新 `Agent.money`，重复点击不会重复发放。
- 用户驳回：必须填写原因，悬赏回到“进行中”，交付截止重新计算 24 小时；原因写入目标进展并作为下一轮写作的修正要求。
- 领取后 24 小时未交付：自动退回待领取、清空领取者，10 分钟后重新抽签征询。被回收居民的目标转为“已放弃”。

### 取消与删除

- 待领取、进行中、待验收的悬赏可由用户取消，进入“已取消”，邀请作废、目标转为“已放弃”。
- 已取消的悬赏可在卡片上删除记录：硬删除 `Bounty` 及其 `BountyInvite`、`BountyDelivery`，删除在 `permanent_deletion()` 内执行，墓碑随 `system_settings` 业务快照同步，其他设备不会复活。
- 只有 `cancelled` 允许删除；已完成等其他状态不可删除，避免误删奖励凭证。

### 与生活目标的关系

- 领取时自动创建一条 `LifeGoal`，`condition={'kind':'bounty','bounty_id':...}`，作为居民日常规划中可见的目标。
- 该目标只能由看板验收结果驱动：模型在生活规划中只能更新进展，不能自行标记完成、暂停或放弃（`life_planner.apply_plan` 拦截）。
- 验收通过置为已完成；驳回保留进行中并写入驳回原因；悬赏取消或回收置为已放弃。

## 2. 状态机

```
open（待领取） ──居民接受(CAS)──▶ claimed（进行中） ──交付──▶ delivered（待验收） ──通过──▶ accepted（已完成）
   ▲                                  │                              │
   │                                  └──────驳回 + 原因──────────────┘
   └────── 24 小时未交付 / 连续失败 3 次 ──────┘

open / claimed / delivered ──用户取消──▶ cancelled（已取消）──用户删除──▶ 记录移除
```

## 3. 数据

| 模型 | 作用 | 关键字段 |
| --- | --- | --- |
| `Bounty` | 悬赏主体 | 目标、要求、文集、分类、奖励、状态、领取居民、交付帖子、邀请时间、24 小时截止、驳回次数、失败次数、最近错误 |
| `BountyInvite` | 抽签顺序与询问结果 | 居民、顺序 `sort`、计划询问时间、状态、决策理由 |
| `BountyDelivery` | 交付与验收事实 | 帖子、执行记录、摘要、验收状态、驳回原因 |

- 奖赏流水复用 `WorldLedger`，业务键保证幂等；不产生支出预算，不计入生活预留。
- 悬赏同步范围为 `system_settings` 业务快照：`Bounty`、`BountyInvite`、`BountyDelivery` 随记录参与三方合并与墓碑。执行租约、线程和本机自动开关仍只在本机，不进入快照。
- 迁移：`system_settings.0081_bounty`。

## 5. 边界

- 一单只给一个居民；不提供多人协作或竞价。
- 悬赏执行不受世界自动执行开关控制，但复用世界执行锁与居民执行租约，避免与其他任务并发抢资源。
- 决策场景 `bounty_accept` 需要同时注册在后端 `routing.SCENES` 和前端 `WorldDecisionModelSettings.decisionSceneLabels`，否则结构化决策恒不生效。
- 驳回不设次数上限；连续执行失败才按 3 次回收。
