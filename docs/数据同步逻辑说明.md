# 数据同步逻辑说明

本文档说明小橘文档「同步与备份」的实际规则：传什么、怎么对齐、何时先拉后推、以及哪些操作会删本地数据。阅读对象是开发者和需要排障的使用者。

相关代码入口：

- 快照导入导出：`utils/sync_manager.py`
- 协议客户端工厂：`utils/remote_storage.py`
- WebDAV / FTP / SFTP 客户端：`utils/webdav.py`、`utils/ftp_client.py`、`utils/sftp_client.py`
- 手动上传/下载：`system_settings/views.py`
- 定时同步与拉取判定：`system_settings/sync_scheduler.py`
- 图书从云端恢复：`anthology/book_views.py`
- 设置页：`frontend_react/src/components/Settings/SyncSettings.tsx`

## 1. 这是什么同步

这不是字段级合并，也不是 Git 式三方合并。

系统把本机导出成一份**远端文件快照**，再用这份快照把另一端对齐过来。一次完整快照包含：

| 远端路径 | 内容 |
| --- | --- |
| `{remote_path}/data_index.json` | 指定应用的数据库记录（Django `serialize` JSON） |
| `{remote_path}/snapshot_meta.json` | 快照 ID、生成时间、来源、系统版本 |
| `{remote_path}/media/` | 资源文件和用户头像 |

同一时间只启用一种协议（WebDAV / FTP / FTPS / SFTP），只写一个远端目录。换协议或换主机 / URL / 远程路径，视为换了一个备份目的地，并清除图书的「已备份」标记，避免把旧目录的标记带到新目录。

远程路径必须手动填写，系统不会填 `/o-doc-backup/` 或 `/o-doc-sync/`，也不会回退到以前用过的目录。留空会拒绝保存；定时任务和手动同步都不会启动。

本地压缩包备份与远端同步分开：

- 导出不依赖远端配置，把当前快照（`data_index.json`、`snapshot_meta.json`、图片/头像/封面等小文件）打成 zip。**图书正文不进压缩包**，避免单本几十到几百 MB 把备份撑爆。
- 导入按压缩包**全量覆盖**：备份里没有的记录会删掉；备份里没有的新字段用模型默认值，不保留导入前本机的新业务。
- 压缩包版本比当前系统**新**则拒绝导入，提示先升级。比当前旧可以导入。
- 备份连接配置仍然不进压缩包，导入不会改 SFTP / WebDAV 设置。

配置存在 `SystemSetting.key = system_webdav_config`（历史 key，不随协议改名）。运行时状态存在 `system_webdav_sync_runtime`。

## 2. 哪些数据会进快照

`SyncManager.TARGET_APPS` 会导出这些应用的全部模型，外加 `auth.Group` 和登录用户表：

- `article`：文章、图片、拍摄组相关字段、批注等
- `anthology`：文集、图书、阅读进度
- `categories`、`tags`
- `assets`：资源记录
- `stats`
- `ai_assistant`
- `system_settings`：Agent、MCP、技能、地理位置等（不含备份连接配置和同步运行时状态）
- `user`：用户资料（含头像路径）

媒体文件按当前数据库里的有效资源记录和用户头像路径收集，上传到 `media/`。图书若已「释放本地、仅留云端」，上传时会保留远端文件，不会因本地没有正文而失败。

**不会**随这份快照走的内容：

- `memos` 闪念
- 站内通知 `message`
- RAG / Chroma 向量库
- 白板若未挂在上述应用模型里，也不会进这份快照

导出用的是 `Model.objects.all()`，**软删记录也会带上**（例如 `Book.is_valid=false`）。界面看不到，快照里还在。

同步配置本身不进快照，也不会被快照覆盖：

- `system_webdav_config`（WebDAV / FTP / SFTP 连接信息）
- `system_webdav_sync_runtime`（上次对齐的快照 ID、拉取/推送时间等）

能连上远端，说明当前备份配置是本机的；换 SFTP 后再对齐旧 WebDAV 快照，不会把协议改回去。

## 3. 三种入口，两种方向

| 入口 | 方向 | 用户意图 |
| --- | --- | --- |
| 设置页「开始上传同步」 | 以本地为准推到远端 | 备份本机 |
| 设置页「从云端下载」 | 用远端快照对齐本地 | 恢复 / 覆盖本机 |
| 定时自动同步 | 先判断要不要拉，再推 | 周期性备份 |
| 「导出备份」 | 把当前数据打成压缩包下载到本机 | 本地全量备份 |
| 「导入备份」 | 用压缩包全量覆盖本机 | 用户自己的备份为准 |

同一时刻只允许一个同步任务。前端点上传或下载前会先保存并测试当前表单配置，避免界面上选了 SFTP、后台还在用上次保存的 WebDAV。

定时同步**不会在进程刚启动时立刻跑**。启动后至少等待 5 分钟才允许第一次自动同步，给用户留出检查或修改备份配置的时间；之后仍按配置的同步间隔执行。手动上传 / 下载不受这个限制。

同步一旦开始会持续执行至完成或报错，界面不提供中途取消，避免半完成传输被误认为有效备份。服务启动后的前 5 分钟不会自动同步，可在这段时间检查或修改备份配置。

保存配置时会测连。测连失败则不写入。更换协议 / 主机 / URL / 远程路径时，会清空本机记录的快照 ID，避免把旧目的地的快照当成新服务器的状态。

## 4. 上传（推）

顺序：

1. 校验本地资源文件是否都还在。记录在、文件不在则中止（`cloud_only` 图书除外）。
2. 读取远端 `snapshot_meta.json`，校验系统版本是否兼容。
3. **仅在满足第 5 节条件时**，先执行一次完整拉取。
4. 上传 `media/` 中应备份的文件，并删除远端多余文件（`cloud_only` 图书正文除外）。
5. 导出数据库为 `data_index.json` 并上传。
6. 写入新的 `snapshot_meta.json`，更新本机 `last_synced_snapshot_id`、`last_uploaded_snapshot_id`、`last_push_at`。

上传本身是「用当前本地覆盖远端快照」。若第 3 步先拉了旧快照，本地会被旧数据改掉，第 4～6 步再把这份被改过的本地推上去，两端都会变成旧数据。

## 5. 上传前会不会先拉远端

会，但必须同时满足下面全部条件（`should_pull_remote_before_push`）：

1. 远端存在有效 `snapshot_id`。
2. 本机已经有 `last_synced_snapshot_id`（说明这个目的地曾经对齐过）。
3. 远端 `snapshot_id` 和本机记录的不一致。
4. 若两端都有时间戳：远端 `generated_at` 必须**新于**本机 `last_push_at`（没有则看 `last_success_at`）。远端更旧则不拉。

不先拉的典型情况：

- 第一次上传，或刚换了备份目的地（快照 ID 已被清空）
- 远端没有快照
- 远端快照就是本机上次推上去的那份
- 远端快照比本机上次成功上传更旧
- 远端快照的系统版本比本机旧（避免用旧版结构先清掉新业务）

设计目的：多机共用一个目录时，另一台先改过远端，本机再上传应先跟上，避免直接盖掉对方。它**不是**「把远端缺的补进来、留下本地多的」。

## 6. 下载 / 先拉（对齐）

「从云端下载」和上传前的预拉取，走同一套对齐，不是合并。

数据库：

1. 读 `data_index.json`，丢掉其中的同步配置项。
2. 按用户名 / 组名 / 内置 Skill / 业务 `userid` 复用本机已有主键，避免管理员账号被另一套自增 ID 顶掉；本机超级管理员密码保留。
3. 快照里**没有的字段**保留本机当前值，不会写成模型默认值。例如旧快照没有 `photo_group_id`，本机已建好的拍摄组不会被拆掉。
4. 把快照里有的记录 `save()`（只覆盖快照里出现的字段语义：缺的字段已先用本机值补上）。
5. 删除本机有、快照里没有的记录。删除顺序会先处理带 `PROTECT` 外键的引用方（先 `Book` 再 `Asset`）。
6. 若远端快照的 `app_version` **低于**当前系统，跳过第 5 步。升级后新建的图书文集、拍摄组等不会因为旧快照没有这些主键而被删掉。

同版本对齐仍会删「本机多出来的记录」。跨小版本从旧备份恢复时，以「旧数据覆盖同主键 + 本机新字段/新记录留下」为准。

媒体：

1. 按对齐后的资源记录和头像路径，从远端补文件。
2. 哈希不一致则覆盖。
3. 删除本地 `MEDIA_ROOT` 里快照未引用的文件。
4. `cloud_only` 图书正文不拉回本地。

因此：本地有、快照没有的文集、图书、图片、拍摄组、头像文件，都会在这次对齐里消失。界面上的「删除」若只是 `is_valid=false`，快照里仍有这条；只有快照完全没有该主键，本机才会被物理删掉。

## 7. 版本兼容

快照带 `app_version`（来自前端 `package.json`）。上传、下载、定时同步在动手前都会先读这份版本。

| 本机 | 远端快照 | 结果 |
| --- | --- | --- |
| 新（如 0.9） | 旧（如 0.8） | 允许。缺的字段保留本机值；上传前不先拉；下载不删本机多出来的新记录 |
| 旧（如 0.8） | 新（如 0.9，另一台已升级并上传） | **禁止上传和下载**。提示先升级本机。不会先拉再推 |
| 相同或只差一个可兼容的小版本 | 同级 | 按第 5、6 节正常对齐 |
| 任意 | 快照没有版本信息 | 拒绝 |

两台电脑、一台先升级并上传时：旧机器不能用自己的结构去覆盖远端。旧客户端没有新字段、新表，一旦先拉再推或直接上传，另一台已经写上去的图书文集、拍摄组都会丢。所以旧客户端在这里必须停住，去升级，而不是继续同步。

## 8. 头像和图书的特殊点

头像存在 `UserProfile.avatar`，一般是 `/media/avatars/...`。上传时按这个路径去 `MEDIA_ROOT` 找文件；对齐时按快照里的路径恢复，并把本地多出来的头像文件删掉。所以：本机刚换了头像，若先被旧快照对齐，新文件会被清掉，资料里可能还指着一份远端没有的旧路径，界面就是裂图。

图书正文挂在 `Asset` 上，外键是 `PROTECT`。书架上的「删除图书」只是软删；「释放本地副本」会删掉本地正文文件，只保留封面和书籍数据。

释放本地副本的条件：同步与备份已配置且该书已标记 `remote_available`（曾经成功备份到远端）。不限定 WebDAV，FTP / SFTP 一样。

备份同步对图书正文的规则：

- **上传**：还没备份过的书会上传正文，并打上远端可用标记。已经标记过、且文件哈希没变的书**不再重复上传**，只保留远端文件。
- **下载 / 对齐**：只同步图书数据和封面。已经释放的本地正文**不会**被整库同步拉回来。需要阅读时，在书架上对该书单独点「从云端下载」。
- 对齐后若正文文件不在本地，该书会保持或改为 `cloud_only`。

## 9. 操作对照

| 你想做的事 | 该点什么 | 不要点什么 |
| --- | --- | --- |
| 把当前本机备份出去 | 上传同步 | 从云端下载 |
| 用远端旧备份覆盖本机 | 从云端下载（会删快照里没有的本地数据） | — |
| 换 SFTP / FTP 目录后再备份 | 先保存并测连通过，再上传 | 只改界面不保存就上传 |
| 两台机器共用一个目录 | 先升级的那台上传；旧版本那台先升级到同一版本再同步 | 旧版本机器对已经更新的快照上传或下载 |

定时同步的判定与手动上传相同。间隔最短 5 分钟。

## 10. 排障要点

1. 同步控制台若出现「先拉取远端数据再继续同步」，说明这次上传先做了完整对齐，不是单纯备份。
2. SFTP / FTP 刷新后又变回 WebDAV：配置没测连成功，库里仍是旧配置。
3. 上传后本机数据变旧：先查 `system_webdav_sync_runtime` 的 `last_pull_at` 是否紧挨在 `last_push_at` 前面。
4. 图书删了界面看不到、同步却还占着资源：查 `books.is_valid=false`。
5. 救数据只能靠更早的 `data_index.json` / `media/` 或 NAS 文件历史。最新快照若已被「先拉后推」写成旧数据，再下载一次会继续按旧快照对齐。
