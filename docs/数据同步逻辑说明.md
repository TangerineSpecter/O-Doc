# 数据同步逻辑说明

本文档说明小橘文档的安全同步 v2：自动同步如何三方合并并保留历史，手动覆盖何时整库采用本机或云端，以及恢复时仍保留的安全边界。

相关入口：`utils/sync_manager.py`、`system_settings/sync_scheduler.py`、`system_settings/views.py`、`frontend_react/src/components/Settings/SyncSettings.tsx`。

## 1. 同步模型

远端目录使用 v2 的不可变快照，而不是用一组可覆盖的根目录文件表示当前数据：

| 路径 | 内容 |
| --- | --- |
| `{remote_path}/sync-v2/snapshots/<id>/data_index.json` | 完整业务数据快照 |
| `{remote_path}/sync-v2/snapshots/<id>/revisions.json` | 每条记录的哈希、修订时间、来源设备和删除墓碑 |
| `{remote_path}/sync-v2/snapshots/<id>/media_manifest.json` | 媒体路径到内容哈希的引用 |
| `{remote_path}/sync-v2/snapshots/<id>/snapshot_meta.json` | 快照 ID、来源、版本、数据与媒体统计 |
| `{remote_path}/sync-v2/blobs/<hash>` | 按内容哈希去重的媒体和图书正文 |
| `{remote_path}/sync-v2/current.json` | 仅指向当前完整快照的指针 |

快照的文件、媒体 blob 都写成功后，才更新 `current.json`。因此媒体上传、数据库合并或快照写入失败时，远端仍指向上一份完整快照。远端保留最近 10 份快照；只在没有任何保留快照引用 blob 时才回收 blob。

`snapshot_meta.json` 同时保存 `index_digest`：修订清单与媒体清单各自的条目数和 SHA-256。同步先读指针、元数据和本机修订摘要；摘要命中时不再下载整份 `revisions.json`，只有摘要不一致、缺少该字段或本机存在待修复修订键时才回退到全量比对。发布仍写完整清单，旧快照和旧客户端继续按原方式工作。

因此，在 WebDAV / FTP / SFTP 的目录浏览器中打开 `snapshots/<id>` 时，只会看到 JSON 元数据；图片、附件、ZIP、头像和图书正文不再按原始文件名出现在 `media/` 下，而是保存在同级的 `sync-v2/blobs/<内容 MD5>`。可通过该快照的 `media_manifest.json` 将原始相对路径映射到对应 Blob。

原根目录的 `data_index.json` / `snapshot_meta.json` / `media/` 是 v1。首次 v2 同步会把它作为只读输入，与本机非破坏性合并后创建首个 v2 快照。v2 发布后，根目录元数据会带更高的应用版本标记，旧客户端必须升级，不能继续写旧格式目录。

手动上传与自动同步统一调用 `SyncManager.sync_v2()`，手动下载调用 `force_download_v2()`。已有 v1 备份由 `_get_legacy_snapshot()` 读取后进入同一 v2 合并或恢复链路；同步写入统一发布不可变快照和 blob。本地 ZIP 导入导出继续使用独立入口。

### 代码职责与提交边界

`SyncManager` 保留同步、覆盖、历史恢复和 ZIP 备份的调用入口，按阶段调用以下模块：

| 模块 | 职责 |
| --- | --- |
| `utils/sync_repository.py` | 远端路径、JSON 文件、同步租约、历史保留与无引用 Blob 回收 |
| `utils/sync_media.py` | 本机媒体发现、图书正文例外、哈希缓存、Blob 上传和校验后恢复 |
| `utils/sync_models.py` | 导出模型范围、本机设置和用户设备字段过滤 |
| `utils/sync_snapshot.py` | 领域检查点、数据库序列化和快照元数据 |
| `utils/sync_merge.py` | 稳定记录身份、三方修订选边、阅读与用量等累积事实合并；不写数据库或媒体 |
| `utils/sync_restore.py` | 数据校验、本机身份复用、整库恢复事务、序列校正和提交后副作用 |
| `utils/sync_policy.py` | 共用异常、未来格式拒绝和取消检查 |

领域校验与整理在编排和恢复阶段执行；纯记录合并不负责修复业务链。农场、小说、学习、量化的同步保护仍由 `SyncManager` 入口按原顺序持有；数据库事务与 `on_commit` 副作用留在恢复阶段，远端租约与发布指针顺序不变。模块拆分不新增持久字段、不改变快照版本或 WebDAV/FTP/SFTP 目录格式。

### 应用版本边界

当前运行系统以 1.5.0 及以上为维护基线，已移除仅服务于 0.9.x → 1.0.x 首次升级的跨主版本特例。同步仍只接受同一主版本下、当前或上一个小版本生成且不高于本机版本的快照；例如 1.5.2 可读取 1.4.x、1.5.0 至 1.5.2，拒绝 1.3.x、0.9.x 和 1.5.3。

运行版本基线不代表历史记录或备份已经转换格式。旧快照读取、历史业务事实校验和数据库迁移仍按各自的数据依赖保留；移除这些路径前须确认没有现存记录或可恢复备份依赖它们。

## 2. 同步前的本机保护

每次手动同步、自动同步和历史恢复前，系统都会在 `MEDIA_ROOT/.sync-v2-safety/` 创建一份完整本机安全归档：

- 含同步范围内的全部数据库记录和 `MEDIA_ROOT` 下的所有文件，包含图书正文。
- 同步、下载校验、合并或恢复失败时不会删除该归档。
- 默认保留最近 3 份。

媒体先下载到临时文件，哈希校验通过后才替换目标文件。同步不会因为本次合并而删除本地未引用媒体；历史淘汰只影响远端不再被快照引用的 blob。

资源和物品图标硬删除时，先在事务内复查引用并删除数据库记录，再在最外层事务提交后清理物理文件；数据库删除失败或事务回滚时保留原文件。公共删除入口在资源锁内检查图片、文章、Agent、提示词、图书和量化等既有引用；移除照片或拍摄组时，其他业务仍引用的共享资源及文件保留，文章、图片、居民头像和历史头像快照中的资源下载链接及完整地址也参与保护。删除前拒绝空路径、绝对路径、越级路径、危险媒体根目录及解析到媒体目录外的符号链接；提交后清理时再次检查路径，并检查是否还有资源记录使用同一路径，仍被引用或检查失败时保留文件。锁内复查拒绝删除时，显式删除接口返回资源正在使用的错误，不报告删除成功。本规则不新增持久字段或同步格式。

本地「导出备份 / 导入备份」仍是另一套用户主动操作：导出不含图书正文，导入是全量覆盖，不参与三方合并。

### 时间编码

数据库快照导出、同步补全字段及小说、学习、闪念、居民记忆元数据统一使用 `utils/sync_datetime.py` 的编码器。日期时间与时间字段沿用 Django 的毫秒精度，但省略全零小数：`12:00:00.000` 输出为 `12:00:00`，有效的 `.123` 和原有时区保留。JSON 业务事实、正文与普通字符串不做全局替换。

生活、烹饪、市场、投资、社交摘要使用同一时间表示，避免导出与恢复后的字符串差异造成误报。市场和投资本机旧摘要仅在严格匹配旧算法时转换；不重建已缺失或被篡改的资产摘要。生活、烹饪旧快照仍先校验原始内容，再转换派生摘要。无需新增字段或数据库迁移。

## 3. 三方合并规则

每台设备在本机保存同步实体状态，不写入业务快照：模型名、主键、内容哈希、修订时间、来源设备和删除墓碑。业务模型保存或删除时记录修订；`QuerySet.update` 不触发保存信号，调用方须同时记录修订，否则「无变更」快路径不会发现这次写入。远端数据写回本机时会抑制新修订的产生，并带入胜出的远端修订状态。

同步输入有三份：

- **Base**：本设备上次共同成功同步的快照。
- **Local**：当前本机数据与本机修订状态。
- **Remote**：`current.json` 指向的完整远端快照。

合并以 `模型:主键` 为粒度，规则如下：

| 情况 | 合并结果 |
| --- | --- |
| 一端新增、另一端未新增 | 保留新增记录 |
| 一端修改、另一端未修改 | 采用修改版本 |
| 一端删除、另一端未修改 | 删除记录，保留墓碑 |
| 一端普通删除、另一端修改 | 保留编辑版本 |
| 一端彻底粉碎、另一端仍保留记录 | 保留粉碎墓碑，包括另一端并发编辑或旧记录重新上传 |
| 两端都修改同一记录 | 修订时间较新的版本胜出；时间相同按来源设备 ID 固定排序 |

手动上传始终发布本机完整快照，不执行三方合并。后端按当前配置的实际远端路径探测 `sync-v2/current.json` 或旧版 `data_index.json`：没有备份时直接首次上传，不显示覆盖确认；已有备份时返回 `confirm_overwrite` 事件，用户确认后直接替换。探测不使用本机缓存的上次同步状态，也不要求解析远端业务数据。首次上传在获取远端锁后再次检查；若期间出现其他备份，转为请求覆盖确认。等待确认的任务回到 idle，不记录为同步失败。系统先保存本机安全快照。能从已有探索结算重建的回顾仍会写入快照；重建不了时保留本机原文并继续上传。构建快照时刷新生活完整性摘要。强制上传不读取、合并或校验远端业务数据，只保留远端格式、快照版本、应用版本和云端图书正文引用这些安全检查。农场播种窗口、种植品质链、战斗目录完整性、生活摘要和「居民记忆来源内容与实际活动不一致」不再中断覆盖。上传前会尽力整理本机：能对齐的播种开工时间会前移，记忆来源会按实际活动重写，生活、社交和烹饪摘要会按当前记录重算。整理不了的只记在同步结果里，快照仍按本机现状发布。云端独有记录会从当前版本移除，旧远端快照仍按最近 10 份的保留策略管理。修订哈希按最终导出内容生成。前端 `forceOverwrite` 经全局驼峰解析后，由后端读取 `force_overwrite`。此操作不新增同步字段或快照 schema。

从云端下载在确认覆盖时整库采用远端快照，同一类领域校验不再拒绝恢复；写入后做同样的尽力整理，让农场、生活和记忆能继续运行。不选择覆盖时走逐条对比：只在一侧出现的记录自动保留，两端都改过的记录返回 `choose_items`，由用户选择本机或云端，也可以整批选用某一侧。未点名的冲突用较新一侧。这次等待选择的任务回到 idle，不记为同步失败。自动同步没有人在场，仍按修订时间自动选边，但也不再因上述完整性问题中断。居民自动记忆仍随整理进度整组采用，避免把记忆正文和进度拆开。更高的 schema 或应用版本、快照格式、路径穿越、同步锁、媒体哈希和体积上限继续拒绝。`repair_farm_queue_window` 与 `repair_agent_world_catalog` 仍可手动预览，日常覆盖和下载不再依赖先跑这两条命令。

单机部署从 `grok-bot/dev` 验收时，不要用「关于」页或 `docker compose pull` 拉 GHCR `latest`。那条镜像仍是 `master` 的正式版本，不含这次覆盖策略。在检出该分支的源码目录构建并改用本地镜像（数据卷保持不动，启动时仍会 `migrate`）：

```bash
git fetch origin grok-bot/dev
git checkout grok-bot/dev
git pull origin grok-bot/dev
docker build -t o-doc:grok-bot-dev --build-arg ODOC_BUILD_COMMIT="$(git rev-parse HEAD)" .
```

部署目录的 `.env` 把 `IMAGE_NAME` 改成 `o-doc:grok-bot-dev`，再执行 `docker compose --env-file .env -f compose.prod.yml up -d`。设置页「上传到云端」在远端已有备份时确认后以本机为准发布；「从云端下载」点「确认覆盖下载」以云端为准写入本机。两条路径都会先写本机安全快照。点「不覆盖，逐条对比」时只列出两端都改过的记录。历史快照恢复和本地压缩包导入仍按原严格校验拒绝残缺快照。

同步读取与本地备份导入均接受当前导出器已生成的战斗快照版本 6，继续拒绝高于 6 的版本；此处仅对齐读写上限，没有提升现有快照版本。

所以 Base 为 A、设备 1 新建 B、设备 2 新建 C 时，合并结果为 A、B、C。远端普通删除 B 而本机编辑 B 时，保留编辑后的 B；若本机没有改 B，则 B 被删除并留下墓碑，后续不会被误认为“本机新记录”重新上传。回收站的彻底粉碎在现有修订 `hash` 字段中使用非十六进制前缀标识，仍保持原有字段长度与快照结构；支持该规则的设备同步时，粉碎会胜过编辑。未更新的设备仍可能按旧规则保留编辑，应先更新参与同步的设备。

首次升级、换新设备或设备离线时间长到共同 Base 已被历史淘汰时，不会把“缺失”直接当删除。系统先做本机安全归档，再以现有修订时间进行非破坏性合并，重新建立共同 Base。

## 4. 数据范围与本机独立项

### 4.1 当前业务模块同步范围总表

2026-10-24 组队冒险使用战斗同步14：`AdventureParty`、`AdventureMember`、`AdventureWave`、`AdventureEvent` 与个人探索／资产事实一起同步，个人结算引用共享事件并双向检查奖励归属。共享帧绑定成员和波次，`AdventureWave.content_digest` 与 `AdventureParty.frame_version` 同步保存：波次变化时更新内容指纹，普通回合组合波次ID、序号与指纹，不重复读取历史原文；导出、同步与恢复仍逐波从完整原文验证指纹及聚合帧。版本1旧队伍按原完整帧校验，下一次业务推进时一次补齐指纹并升级版本2；旧快照缺少字段时明确采用版本1与空指纹，不继承较新的本机值。事件链分叉拒绝逐行合并，改用完整来源快照；原有放宽回顾策略不绕过组队一致性校验。运行授权、租约继续使用不同步的 `CombatRuntime`，下载后不自动执行。迁移0092、0093，引擎6、内容包combat-1.0.22；所有同步设备升级后使用。旧快照没有队伍表可正常恢复，旧在途与历史不重算。

| 业务模块 | 状态 | 已同步或未同步的数据 | 原因与边界 |
| --- | --- | --- | --- |
| 文章与文章关联数据 | 已同步 | `article` 应用中的文章、文章资源关联、图片、批注、批注评论、文章评论、评分和 `ArticleVersion` 等模型；软删状态也同步 | 属于核心知识内容，按记录参与三方合并；关联文件是否进入 Blob 由资源媒体规则决定 |

| MT4 回测文集 | 已纳入同步实现 | EA 档案及结构化最低要求、参数、回测记录、交易事件、附件引用和备注及 HTML、图片、EA 文件 | 用户已确认全部同步；使用 `quant_schema_version=78` 校验私密归属、要求字段、附件引用及备注，文件随 `Asset` 媒体清单同步。详见 [MT4 回测文集](./quant/MT4回测文集说明.md)；远端两设备验收另行执行。 |

文章和闪念的本机 Chroma 集合按默认 Embedding 模型签名隔离，避免切换不同维度模型后复用固定维度的集合。旧集合保留，当前模型所需索引仍在既有恢复窗口内分批重建；删除内容时会同时清理旧模型及旧版集合，避免切回旧模型后重新检索到已删除内容。文章恢复若发现正文、标题、文集或有效状态在请求期间变化，会清理本次过期版本的向量并保留重试条件；成功修改 RAG 同步标记后按文集刷新统计。这些处理仅改变本机索引组织与既有派生统计，不新增数据库字段或 WebDAV 同步字段。

`SyncManager.TARGET_APPS` 导出 `article`、`anthology`、`categories`、`tags`、`assets`、`prompts`、`stats`、`ai_assistant`、`system_settings`、`user`、`book_analysis`、`whiteboard`、`memos`、`message` 的业务模型，以及 `auth.Group` 和用户表。软删记录也会随快照保存；其中 `book_analysis` 的本机缓存、任务、租约和执行事件由本机模型排除清单过滤。

图片组编辑在修改任何图片或清理资源前校验提交的已有图片 ID：重复、未知或不属于当前组的 ID 会被拒绝，不写入图片、文集计数或同步修订。合法编辑继续使用原有图片、资源和修订同步规则；不新增持久字段或同步格式。

单张图片创建时，图片记录、文集计数和同步修订在同一数据库事务中完成；失败时全部回滚。单张图片删除、图片组编辑或删除时，图片软删、组内单图降级、资源记录处理、文集计数与同步修订在同一数据库事务中完成；事务失败时全部回滚。媒体文件和图片搜索索引在最外层事务提交后清理，回滚不会清理文件或索引。已有图片及资源字段和同步格式不变。

PostgreSQL 下，拍摄组创建、编辑、删除以及单图创建、编辑、删除先按文集加行锁，再读取照片当前状态；单图跨文集编辑先按图片序列化字段校验并规范化目标文集 ID，再按文集 ID 排序加锁；可接受的数字 ID 转为字符串后参与锁集合，空值、布尔值、数组和对象等非法输入在加锁及写入前返回 HTTP 400。并发删除不会重复扣减计数，过期的组成员不会被重新写入。SQLite 不提供等价的行级锁，并发写入仍受其数据库级锁和超时约束。

单张照片跨文集移动时，照片归属、两边文集计数和同步修订在同一事务中更新。照片从原拍摄组脱离，原组仅剩一张时同时降级为单图；失败回滚全部变更。图片搜索索引属于本机派生数据，原索引的文集与照片当前文集不一致时沿用既有逻辑显示为待更新。

创建拍摄组时，允许加入当前文集的已有照片；若照片来自其他拍摄组，原组仅剩一张时在同一事务内降级为单图。原组仍有多张时保持原组关系，失败回滚新旧组及同步修订。

`article.ArticleVersion` 是独立的业务记录，快照标题、Markdown 正文、文集、分类、标签 ID、摘要、字数、操作者和来源，使用跨设备稳定的字符串主键参与三方合并。每篇文章最多保留 5 个历史版本；淘汰旧版本使用删除墓碑，避免离线设备再次同步时将其带回。版本正文进入 `data_index.json`，不作为媒体文件上传 Blob。新增此模型的版本为 0.9.14；参与同步的设备需先升级，旧客户端会按应用版本校验拒绝写入新快照。

`article.ImageReview` 是照片评价的业务记录，从 0.9.20 起随 `article` 进入快照。一条记录对应一个 Agent 对一张照片的评语、六项分数和该条综合分，使用由照片 ID 与 Agent 标识确定的字符串主键，并按照片与 Agent 标识唯一，避免两台设备独立首次评价后合并时产生唯一约束冲突。删除照片时评价级联删除，并使用删除墓碑。识图索引和识图任务仍只留在本机。参与同步的设备需先升级到 0.9.20，旧客户端会按应用版本校验拒绝写入新快照。

同步恢复会显式写入快照中的主键；PostgreSQL 恢复事务会暂时锁定实际恢复过的自增主键表，并在结束前按当前表内最大主键重置序列，避免并发写入或后续创建阅读统计、通知等记录时与快照主键冲突。此处理不新增同步字段，也不改变快照格式。

白板从旧版浏览器 `localStorage` 升级时，前端会在首次成功连接服务端后导入旧 `odoc-whiteboards` 数据；导入成功才移除旧键，并保留 `odoc-whiteboards-legacy-backup-v1` 作为可恢复备份。后续白板列表、编辑保存、AI 洞察和统计均以服务端记录为准。

`prompts` 包含提示词模板、专用分类/主题/标签、显式主题和标签关联、效果使用记录及结果图关联；模板和效果记录的软删状态同样进入删除墓碑。效果图仍由 `Asset` 进入媒体清单和 blob，彻底删除提示词记录只会清理没有文章、图片、Agent、图书或其它提示词结果引用的 `prompt` 来源资源。恢复快照时，模板封面会在结果图恢复后第二阶段写入，避免循环外键阻断新设备同步。

文章配图的 `PendingArticleIllustration` 仅保留在当前设备，包含 Grsai 生成中任务或 Grsai/New API 下载失败的任务 ID、模型 ID、服务类型、状态、可能过期的图片 URL、预览许可和错误信息；不进入 WebDev 快照或修订追踪。下载成功后生成的普通 `Asset` 与图片文件按现有资源规则同步。

配图调度使用已有 `next_attempt_at` 字段原子认领任务，执行期间将其暂设为 10 分钟后，避免同一数据库上的多个进程重复生图；进程中断后，认领到期可恢复。此字段仍属于本机任务状态，不新增同步字段。

`system_settings` 中的 Agent 配置、任务、执行记录和 Agent 世界精选动态属于用户历史数据，会随快照同步；执行过程中的临时线程状态和调度器运行状态不进入快照。

从 `system_settings.0074` 起，`AgentTask.mcp_tool_scope` 随 Agent 任务记录进入 WebDev 快照和修订追踪，保存自定义任务按 MCP 服务 ID 列出的允许工具名称。`null` 表示兼容旧任务：使用所选 Agent 绑定的全部已启用 MCP 工具；`{}` 表示严格禁止 MCP；非空对象只开放对应服务下列出的工具。设置界面/API 新建自定义任务默认写入 `{}`；迁移不回填已有记录，缺少该字段的旧快照反序列化为 `null`，保留旧行为。服务和 Agent 的既有启用状态仍优先，白名单不能单独启用它们。字段属于已同步的 `system_settings` 目标模型，沿用自动序列化，不增加独立运行状态或同步表。参与同步的设备应先升级到包含 `system_settings.0074` 和应用版本 1.2.14 的版本；1.2.13 及更旧客户端会由现有应用版本兼容检查阻止其写入较新快照。

评论动态补录以评论 ID 为业务身份，兼容早期 `run:…:tool:…` 与 `legacy:post-comment:…` 事件键。同一 Agent、同一评论的旧动态会归并到 `comment:<评论ID>`；已有该事件键时保留其主键与立场，补齐旧记录的执行关联和元数据，并通过 ORM 删除多余动态、记录同步删除墓碑。仅有旧动态时复用其主键，不另建一条。不同评论 ID 即使内容相同也不合并。本次不新增同步字段或模型。

删除 Agent 时，公开历史记录在同一删除事务中固化最后的名称与头像：作品、评论、评分、划线批注与回复复用已有作者快照，照片评价新增 `ImageReview.agent_avatar`（`article.0024`），动态使用已有 `metadata.agentSnapshot`。这些资料均随所属业务记录进入 WebDAV 快照；删除失败时固化和删除一起回滚。照片评价的 `agent_key`、记录主键以及作品/评论的稳定作者标识保留，不改变历史业务身份或唯一约束。新批注使用 `agent-id:<ID>`；删除时能明确归属的旧批注名称身份转成稳定 ID，防止同名新 Agent 接管。历史头像引用也参与资源删除保护。`system_settings.0032` 为仍关联 Agent 的旧动态和照片评价补快照；已失联记录仅按作品、评论或批注的明确作者回退，无法确定时展示“历史作者未关联”，不猜测归属。所有同步设备应升级并执行上述迁移。

同步写回或备份恢复在 `suspend_tracking` 范围内清理本机多余 Agent 时，不执行本机作者固化，以免用本机旧资料覆盖导入的作者快照。头像的全量历史引用仅用于删除保护，读取权限独立按所属文章、照片文集的可见性检查；历史工作动态头像沿用动态接口的登录限制，不因被私有内容引用就公开资源。

从 0.9.24 起，Agent 任务的 `schedule_mode`、`random_period`、`random_count`、`random_allocations`、`random_cycle_snapshot` 和执行记录的 `random_context` 随业务快照同步。它们描述周期随机调度配置、串行 Agent 次数分配、当期不可变的周期标识/边界/配置额度及排程起点，以及执行记录所属周期和随机机会；每个 Agent 的成功状态仍记录在 `agent_runs`。参与同步的设备需先升级到 0.9.24，旧客户端会按版本校验拒绝新快照。

`system_settings.AgentRandomRuntime` 是本机随机调度状态，包含当期配置的本机副本、随机计划、已完成机会、不可执行 Agent、失败退避与执行租约，明确排除 WebDAV 快照和同步修订追踪。它用于保持重启前后的计划及去重；恢复时用任务的当期配置快照重建计划，避免待生效配置提前生效；同步来的执行记录按机会和 Agent 归并成功次数，也恢复 Agent 删除后的跳过标记。同一数据库通过原子租约避免重复认领，WebDAV 快照不提供多台离线设备之间的实时互斥，同一随机任务应只在一台设备运行。

从 0.9.23 起，Agent 的 `money` 余额以两位小数随 Agent 配置进入 `system_settings` 快照。升级迁移将已有 Agent 余额初始化为 `10000.00`，新建 Agent 默认也为 `10000.00`；参与同步的设备需先升级到 0.9.23，旧客户端会按应用版本校验拒绝写入新快照。

0.9.16 新增 `AIModel.type=image_generation` 和 `system_ai_config.defaultImageGenerationModelId`，默认生图模型随 AI 配置同步。参与同步的设备需先升级到包含此版本的客户端，旧客户端会按应用版本校验拒绝写入新快照。

界面字体和悬浮菜单风格属于当前浏览器的本地外观偏好，保存在 localStorage，不进入 WebDAV / FTP / SFTP 快照。悬浮菜单未设置时使用经典小橘子，可在常规设置中切换为橘子妹子。

以下内容不在业务快照中：

- 同步连接配置 `system_webdav_config`
- 同步运行状态 `system_webdav_sync_runtime`
- 本机设备 ID 和同步实体状态
- `knowledge_maintenance`（每日回顾状态与健康问题忽略记录）、RAG / Chroma 向量库，以及不属于上述模型的浏览器本地派生数据

知识维护数据属于设备本地的派生状态：每日回顾可依据当前内容重新生成，健康问题由实时扫描得出；因此一期不加入 WebDAV / FTP / SFTP 快照，也不会影响现有内容实体的同步与冲突合并。

更换协议、服务器或远程路径视为切换备份目的地，会清空本机记录的共同 Base 和图书远端可用标记。远程路径必须显式填写。

## 5. 媒体与图书正文

### AI 图书导读

`book_analysis` 的分析设置、章节定位、分析版本、章节成果、图谱节点 / 关系 / 出处和人工修正加入同一快照与修订追踪。字符串 ID 跨设备稳定，重新分析不覆盖人工修正。所有同步设备需先升级到包含此领域的版本。

传记模式的确认传主、版本传主和可核对原话 `BiographyQuote` 同属已发布业务数据，进入相同快照与修订追踪；原话的正文位置与归属证据随记录同步。旧快照没有这些字段时由迁移补默认值。同步设备需先升级至包含传记迁移的版本，再共享该模式的结果。

正文缓存 `SourceCache`、分段缓存 `SegmentCache`、本机任务 `AnalysisRun`、执行租约 `WorkerLease` 与执行诊断事件 `ExecutionEvent` 明确排除同步；Chroma 向量也是本机派生数据。执行事件不进入本机同步修订追踪或远端快照。新设备可直接浏览已发布导读、图谱和证据，全文检索需按需恢复图书正文并重新建索引。自定义章节拆分 / 合并保留原始区域定位，可在无缓存的设备重建。更换正文时旧版成果不用于当前分析，历史版本保留只读查看。

### 原样 HTML 笔记（0.9.8 起）

转换副本的内部字段 `enforce_note_privacy=True` 随 Article 全字段快照同步，使 Markdown 副本实际继承文章权限；历史 Markdown 默认 False，访问行为不变。部署须执行迁移 `0015_article_enforce_note_privacy`，各设备均须更新本次完整版本。副本编辑保存会移除不再出现在正文中的 material 关联，避免失效关联阻止 HTML 专属资源回收。

文章的 `content_format` 默认为 `markdown`，原样笔记为 `html`；`content` 仍是提取后的 Markdown。`ArticleAsset` 使用 UUID 主键记录 `source`（HTML 原文件）、`preview`（静态安全预览）、`material`（图片、字体及样式文件）和 `package`（ZIP 原包）的多对多引用。Article、ArticleAsset 与 Asset 都进入现有三方快照与删除墓碑，全部有效文件进入媒体清单与 blob；转换副本只继承正文实际引用的素材。

旧快照缺少 `content_format` 时，新设备按 Markdown 读取；已有设备的字段按现有缺字段合并规则保留。0.9.8 快照通过现有应用版本检查阻止 0.9.7 及更早客户端写回，所有参与同步的设备应先升级。没有提升快照格式号，不改变 WebDAV / FTP / SFTP 的存储布局。

HTML 删除不提供业务回收站。仅回收带 `html_import_owned` 标记且没有任何其他有效引用的资源；源/预览/关联记录的删除随墓碑传播。接收删除快照的设备也会清理专属本地文件，失败保留无效 Asset 上的 `html_cleanup_pending`，可执行 `python manage.py cleanup_html_resources` 重试。文件清理再次检查引用并校验业务媒体目录；同步恢复出的有效引用会阻止清理。历史快照和本机安全归档仍按既有策略保留，不代表前端提供恢复按钮。

HTML 文件不得通过裸媒体目录执行：内置 `/media/html_notes/` 路由拒绝直接访问，预览必须走文章授权接口和无脚本 sandbox iframe；若部署反向代理直接映射媒体目录，务必同样禁止 `/media/html_notes/` 并将业务资源访问交给 `/api/resource/` 权限接口。

有效资源和用户头像会按内容哈希上传到 blob 目录；相同内容只上传一次。快照只保存引用，保留历史不会复制大图或图书正文。

图书正文采用按需下载：同步与「从云端下载」不会自动把大文件拉回本机。`cloud_only` 图书正文允许本机不存在；系统保留上一个快照中的 blob 引用，用户在书架阅读或点击「从云端下载」时才下载并校验哈希。图书释放本地副本仍要求其曾成功同步并具有对应远端内容。

### 图书文件丢失与补传

图书正文和普通附件的丢失策略不同：图书是用户可手动管理的大文件，因此不会因正文缺失阻断整套数据同步。

| 情况 | 系统行为 | 用户可执行操作 |
| --- | --- | --- |
| 本机正文缺失，云端副本可用 | 书架条目保留并标记为「仅云端」 | 阅读时按需下载 |
| 本机正文缺失，云端副本也无法下载 | 书架条目保留；同步仍可继续 | 在书架菜单选择「从本地文件补传」并选择同格式文件 |
| 本机仍有文件，但远端副本被手工删除或失效 | 不信任旧的“已备份”标记 | 选择「从本地文件补传」；下一次同步会建立新的云端副本 |
| 图书封面缺失 | 清除封面引用，使用书架默认封面 | 无需处理，不阻断同步 |

补传先安全地写入本机媒体目录，并重置该书的远端可用标记；随后由下一次手动或定时 v2 同步把正文写入 blob 和新快照。若本机、云端及其他备份来源都没有正文，系统无法凭书架元数据还原内容，用户可以保留条目待日后补传，或主动从书架删除。

## 6. 入口、并发与启动保护

设置页「上传到云端」、 「从云端下载」和定时任务都走 v2。确认「强制覆盖云端」时以本机完整快照替换远端当前版本；确认「确认覆盖下载」时以云端快照整库写入本机。这两次都不做三方合并。未确认覆盖时，若远端当前快照就是本机上次对齐的那一版，并且修订清单和媒体哈希都没有变化，任务直接结束，不打包、不下载整库、也不发布新快照。备份配置、同步运行状态和设备标识只留在本机，不参与这次比较。只有本机在这之后改过数据或媒体时，才导出一份新快照并上传变更的媒体。远端头已由其他写入推进、且这次没有选择覆盖时，仍做三方合并；两端都改过的记录在手动对比里交回选择。

同步配置中的服务总开关控制同步服务是否可用；「启用定时同步」是独立开关。关闭后不会运行后台定时任务，但仍可在设置页手动上传或下载。历史配置没有该字段时按开启处理，以保持升级前的行为。

同一时刻只允许一个同步或历史恢复任务。设置页可请求终止卡住的同步：任务会保持“正在终止”占用，直到当前网络调用返回、同步线程实际释放远端锁后才允许开始下一次任务。媒体恢复、数据库合并和新快照发布属于不可中断提交段；若终止请求在此期间到达，任务会先完整提交，避免留下媒体与数据库不一致的本地状态。终止不会破坏已发布快照。WebDAV 建连检查、目录创建和同步锁请求最多等待 8 秒；文件传输仍使用 30 秒超时，FTP / SFTP 也使用各自的 30 秒超时，界面会依次显示安全快照、远端锁、快照读取、媒体校验和快照发布等阶段。系统启动后至少等待 5 分钟才开始第一次自动同步；手动同步和保存已验证的配置不受此限制。

自动同步失败后以配置的同步间隔为基数逐步延长重试时间，最多等待 24 小时；连续 5 次失败后暂停本机的自动任务，但不修改用户设置中的定时同步开关，手动同步仍可使用。达到暂停条件时向管理员发送一条系统通知。保存通过连接测试的配置或任一方向的手动同步成功后会清除本机失败计数并恢复自动重试；连接状态、退避时间和暂停状态不进入业务快照。

本机同步执行者持有 `MEDIA_ROOT/.sync-v2-runtime/active.lock` 文件锁，任务身份写入锁文件；上传、下载、自动同步和导入／历史恢复在退出路径释放本机执行锁。新任务的存活判断使用该文件锁，进程退出或容器重启后，操作系统释放锁，不依赖可能复用的 PID 或变化的容器主机名。旧版无执行凭证的任务仍按进程与失效时间识别，但失效结果会持久化，避免接口判断“不在运行”而页面仍读取到 `running`。已终止的失效任务回到 idle，清除取消标记及“正在释放”的错误提示；主动终止不计入自动同步失败次数。

若异常退出留下远端同步锁，本机运行时仅保存遗留任务身份 `abandoned_runner_id`，供下次手动或自动同步恢复。恢复须同时核对远端锁的 `device_id` 与遗留 `runner_id`，不会因设备相同就删除另一任务的锁。该本机运行时记录、执行凭证文件及取消状态均不参与 WebDAV 业务同步。重复点击终止只保持原取消请求，不会强行放行仍活着的执行者。正常终止返回 `cancelled` 流终态；数据提交段已经开始时仍须完整提交后才能退出。

本机文件被手动清理或开发环境重置后，不会阻断同步：图书正文会标为仅云端可用，封面会回退默认封面，其他缺失附件/图片会软删除资源记录，缺失头像会回退默认头像。该状态会随下一份快照同步，不会继续把已不存在的文件引用带到其他设备。

## 7. 历史与恢复

已登录用户可在设置页查看最近 10 个远端快照（时间、来源设备、触发方式、应用版本、数据数、媒体数）。恢复某一版本前必须明确确认：系统先创建本机完整安全归档，再下载并校验该版本媒体，在数据库事务中写入数据和修订状态，最后把恢复结果发布成一个新的当前快照。旧历史快照不会被覆盖。

历史恢复读取时校验农作物元数据与来源数据，残缺新版在媒体恢复前拒绝。恢复后重新导出数据库中的实际结果并计算匹配的修订哈希，再生成当前版本元数据；旧库存补一星、关闭旧会话及版本保留清理等归一化结果均进入新快照，不再直接重新发布历史原文。此修复不新增持久化字段或同步实体。

同步状态会记录当前快照 ID、共同 Base、最近合并的新增/更新/删除/冲突数量，以及最近本机安全归档路径；同步日志也会展示这些合并统计。

## 8. 版本兼容与排障

v2 快照携带应用版本。远端快照由更新系统生成时，旧客户端会拒绝同步；首次 v2 发布也会阻止仍使用 v1 的客户端继续写同一目录。遇到版本提示时应先升级客户端，不能用旧客户端上传。

SFTP（2026-10-22）：仅明确的 `ENOENT` / 文件不存在可解释为无文件或空目录。权限不足、超时和连接中断不再被当成首次上传依据；文件读取和存在性检查明确失败，目录列举返回失败状态，目录创建也不再吞掉异常。多个设备同时创建共享目录时，复查确为目录即可继续。此调整不新增字段或协议。`system_settings/test_sftp_sync.py` 使用内存 SFTP 服务覆盖自动首次合并、增量与无变化跳过、手动覆盖、传输失败释放锁后重试及读取失败保护；真实 SFTP 服务器仍需部署后验收。

自动同步失败按原有间隔退避重试，连续五次失败会暂停；成功的手动上传、下载或连接测试会清零失败与暂停状态。因旧校验连续失败而暂停的设备，升级后可先完成一次手动上传或连接测试以恢复自动同步。

排障优先顺序：

1. 查看同步状态中的错误、合并摘要和本机安全归档标识。
2. 在设置页确认当前指针和历史快照是否存在，再决定是否恢复历史。
3. 媒体校验失败、磁盘写入失败或数据库事务失败时，不要重试旧客户端；保留安全归档，修复存储或磁盘问题后再执行 v2 同步。
4. 若某类数据不在第 4 节范围内（例如闪念），它不会被此同步保护，应使用其独立的备份方式。

`WorldActionRuntime` 的 `post-photo:` 记录负责本机补图授权与锁，明确不同步；轮询时间与等待计时仅存进程内存，不写入快照。恢复同步数据后撤销本机补图授权，管理者必须显式查询原请求或在确认失败后重新生成，避免另一设备自动产生费用。

### 手动上传来源校验修正（2026-10-18）

手动“上传到云端”只校验本机导出的完整快照，空远端不会触发合并校验；以下两类校验曾把运行正常的本机数据误判为不完整，现统一与运行时规则一致：

- **农场种植队列**：来源校验改用 `normalized_rules` 归一快照里的 `FarmCatalog.rules`，与运行时 `catalog_for` 一致。旧库保存的目录可能缺少后加入的内置作物或肥料，运行时会在内存中补齐，但导出的是库里原始值，旧逻辑因此报“种植项目必须引用现有种子SKU”。真正引用不存在作物的队列仍然拒绝，错误信息会带上居民、计划日期和出错的SKU。
- **生活来源摘要**：`checkpoint_all` 对所有拥有生活记录的账号生成 `LifeIntegrity`（不再只看 `LifeConfig`）。仅有资料、目标、周期或安排而无配置的账号，导出前按运行时 `config_for` 的默认值补建配置并记录警告；已无任何生活记录的账号，其遗留摘要被清理。校验失败信息会列出缺少摘要的账号，或摘要不一致的账号与数据表。

历史快照恢复和本地压缩包导入仍走严格校验。手动覆盖上传、覆盖下载和未覆盖时的逐条对比不再因这些领域问题中断，见上文「强制上传」。引用不存在作物的队列不会被静默改成别的作物；对不齐且无法安全前移开工时间时，同步继续，并在结果里说明。

### 旧农场目录一次性补齐与修复命令（2026-10-18）

```bash
python manage.py repair_agent_world_catalog                 # 只预览，不写库
python manage.py repair_agent_world_catalog --apply         # 备份受影响记录后修复，并复用手动上传的校验
python manage.py repair_agent_world_catalog --apply --drop-unmappable  # 另外移除目录与内置作物都不存在、尚未播种的队列项目
```

命令报告缺少内置项的目录、引用未知 SKU 的队列项目（居民、日期、SKU）、缺少 `LifeConfig` 或摘要孤立/不一致的生活账号。`--apply` 在同一事务内补齐目录、补建默认生活配置、刷新摘要并清理无记录的遗留摘要，然后调用与手动上传相同的本机快照构建和来源校验；失败则整体回滚。行级备份写入 `SYSTEM_LOG_DIR/catalog-repair-backups/`，可用 `loaddata` 恢复。不存在旧 SKU 映射关系，无法映射的项目默认只报告；`--drop-unmappable` 逐条列出被移除的项目，已有播种记录的项目拒绝移除。

### 播种窗口与上传快照的一次性对齐（2026-10-17）

日程页只看安排和农场操作是否成功，不比较播种时间是否落在开工标记与当天截止之间。快照时间仍按 `activated_at <= 播种时间 < cutoff` 理解窗口。某一天的安排可以全部成功，而这条窗口对不齐，常见原因是开工与第一笔播种共用同一时刻、毫秒以下被截掉，或容器时区与上海墙钟把同一时刻记成两套时间。强制覆盖上传、覆盖下载和逐条对比都不再因此中断；同步会尽力把开工标记前移到不晚于最早一笔播种。`validate_queue` 仍供运行时和手动修复命令使用，不再作为覆盖同步的前置门槛。

`repair_farm_queue_window` 只修这一处旧数据。默认预览全部居民；`--apply` 必须指定 `--agent`（可加 `--day`），或在看完预览后加 `--all`。能修时只把该计划的开工标记及对应开工记录前移到不晚于最早一笔播种的快照整秒，播种记录、进度、地块和库存不动。只有播种快照时间不早于截止时，才把那笔 `created_at` 收到截止之前。不删除计划或播种，不另造开工记录。修复后用同一条队列校验复查，失败则整批回滚。SQLite 会先复制 `.bak-时间戳`；PostgreSQL 请先 `pg_dump`。行级备份在 `SYSTEM_LOG_DIR/queue-window-repair-backups/`。

Docker 部署在 `o-doc` 容器内执行（Compose 服务名是 `app`）：

```bash
docker compose exec app python manage.py repair_farm_queue_window
docker compose exec app python manage.py repair_farm_queue_window --agent agent_yTiYFkvQZO --day 2026-10-13
docker compose exec app python manage.py repair_farm_queue_window --agent agent_yTiYFkvQZO --day 2026-10-13 --apply
```

预览若还列出其他计划，只修 2026-10-13 后上传会停在下一条。看完列表再执行 `repair_farm_queue_window --all --apply`。容器名是默认的 `o-doc` 时，也可以写成 `docker exec o-doc python manage.py repair_farm_queue_window`。

### 本机 SQLite 连接配置

SQLite 连接在建立时设置 5 秒忙等待，尝试将库文件切换为 WAL，并在本连接使用 `synchronous=NORMAL`。WAL 模式持久保存在库文件中；首次切换若发生数据库操作错误，会记录警告并保留当前日志模式。内存数据库仍使用 SQLite 支持的内存日志模式。`NORMAL` 在 WAL 下保持事务一致性，但断电时最近已提交事务可能丢失，不提供 `FULL` 的同等持久性保证。

这些是本机存储运行参数，不是业务字段，不加入 WebDAV/FTP/SFTP 快照。现有同步和本地 ZIP 备份导出逻辑数据，不能把运行中的 SQLite 主文件单独复制当作完整备份；需要文件级备份时使用 SQLite backup API 或停库后处理 WAL 文件。PostgreSQL 连接不应用这些参数。
